# R03 · 中台共享能力契约

> **本项目最该先读的一份**。回答一个具体问题：**同一家公司的 floorplan 中台，哪些能直接拿来用、
> 哪些改了才能用、哪些必须新建、哪些绝对不能碰**。

## 1. 引用口径

- 凡写「floorplan 资产」一律理解为**基线事实**（它确实存在），**不等于本项目已复用**。
- 路径以 `../floorplan-system/` 为根；类名、表名、枚举名照抄，不改写。
- 四分类标：**✅ 直接复用 / ⚠️ 扩展后复用 / ❌ 必须新建 / 🛑 明确废弃**。
- 「可直接复用」= 改包名/配置即可，机制不变；**不是**「把 jar 加进依赖就完事」（见 §6 抽取前置）。
- 三处隐性冲突（§4）是**合规事故级**，必须在共享库分叉时显式切断，不能用「看起来能跑」验收。

## 4. 三处「看起来能跑、合规上已经出事」的隐性冲突（**必须显式切断**）

> 这三处是复用时最危险的地方：代码能编译、接口能返回 200，但已经违反 APPI / 主体法理。
> 切断动作必须在 **S1 抽取共享 jar 时**完成，并写进验收断言（`R10` A-xx）。

### 切断点 ① — 事件载荷硬编码 `vin`

| 项 | 内容 |
|---|---|
| floorplan 现状 | `common/event/JsonPayloadReader.requireVinAndTraceId()` 在写库前**强制 payload 含 `vin` + `traceId`**，缺失抛异常；`LoanCreatedCommand` 以 `vin/advanceId` 为键；`V21` 迁移注释同口径 |
| 冲突 | C 端事件主键是 `applicationId` / `contractId` / `loanId` / `releaseOrderId`，**没有 VIN 业务主键**；更严重的是 outbox 表跨模块共享且 `SENT` 行永久保留，若为了绕过校验把客户身份塞进 payload，等于把 PII 写进永久留痕的消息表 |
| 切断动作 | 新增 `requireBizKeyAndTraceId(bizKeyName)`，默认 `applicationId`，按事件类型配置；**保留必填校验但不硬编码 vin**；新增 payload 白名单校验（禁 PII），见 `ADR-RF-007` / `R09 §5` |
| 验收 | INV-4 扫描 payload 键；命中白名单外即失败 |

### 切断点 ② — `Dealer` 法人假设

| 项 | 内容 |
|---|---|
| floorplan 现状 | `DealerApplicationService.java:30-31`「借款人是法人经销商，不适用个人借款的总量规制」；`dealers` / `credit_lines` 以 `dealer_id` 归户；Q12 明确不采集个人身份信息 |
| 冲突 | C 端主体是**自然人**，适用（或有适用可能）分期付款销售法支付能力预估额 / 贷金业法总量规制；主体模型、归户键、审查规则链全部不成立 |
| 切断动作 | 不 import `com.company.floorplan.*.Dealer` / `CreditLine`；新建 `Customer`(PII) 与 `AffordabilityAssessment`；`DealerPartner` 仅作**加盟店主数据投影**，不是债务人 |
| 验收 | 全仓 grep 无 `floorplan` 包 import；`customers` 表无 `dealer_id` 归户列 |

### 切断点 ③ — 员工 RBAC 套到客户身上

| 项 | 内容 |
|---|---|
| floorplan 现状 | 14 个 `UserRole` 全是内部岗位；`auth-service` 只发员工 token；`audit_events.actor` = 操作员工号；`JwtAuthInterceptor` 把 `perms` 放进 token |
| 冲突 | 客户是自然人外部主体。直接复用会把客户当内部角色发 token，或把客户自助操作记成员工 `actor`，**审计链与 APPI 同时失效** |
| 切断动作 | 双主体：员工侧沿用 RBAC 机制（枚举重写）；客户侧独立 `CustomerIdentity` / OTP / eKYC / 同意会话，**独立 issuer + audience + 密钥**；审计 `actor_subject` 四类（`ADR-RF-004`） |
| 验收 | 客户 token 在员工端点必须 401/403；员工 token 在客户端点必须 401/403；审计记录主体类型可区分 |

### 附：切断点 ④（工程性，非合规）

floorplan 的 `web` 模块内有一批**同名旧版横切类**（`web/dto/ApiResponse.java`、`web/config/JwtAuthInterceptor.java` 等），
与 `common` 版并存。抽取共享 jar 时**只取 `common` 版**，二选一，不许两套一起搬。

## 6. 共享内核治理（`company-platform-contracts` · ✅ S1-W1 已抽取）

### 6.1 内容边界（**只放机制，不放语义**）

```
company-platform-contracts/
├── response/     ApiResponse<T> · 分页包装
├── exception/    BusinessException 基类 · 全局异常骨架 · 错误码接口（不含枚举内容）
├── security/     JwtAuthInterceptor 机制 · AuditActor · @RequirePermission 注解 · 主体类型枚举
├── event/        DomainEvent · EventConsumer · OutboxPublisher 端口 · JsonPayloadReader（可配置 bizKey）
├── idempotency/  IdempotencyKeyResolver · CONFLICT 语义
├── calendar/     BusinessCalendar 端口 + holidays 表结构范式
├── crypto/       字段级加密端口 + AES-GCM 工具 + mask()
├── storage/      AttachmentStorage / DirectUploadEndpoint 端口
├── audit/        AuditEvent 结构 · append-only 约定
└── convention/   金额 BIGINT / 时间 TIMESTAMPTZ / 枚举 RowMapper / 不物理删除 的规范文档
```

**明确不放**：`Permission` 枚举内容、`UserRole`、`ErrorCode` 内容、任何 `Dealer`/`VehicleUnit`/`Loan` 实体、
任何 VIN 语义、任何 B2B 或 C 端业务规则。

### 6.2 抽取原则（不能动摇 floorplan）

1. **新增 artifact，不改 floorplan 现有包**。floorplan 继续用 `com.company.floorplan.*`；抽取产物用 `com.company.platform.*`。
2. 先把机制类**复制 + 泛型化/参数化**（`requireBizKeyAndTraceId`、主体类型、错误码接口），再让 RF 依赖新 artifact；
   floorplan **不强制迁移**，避免其 0 bug / 全量冒烟基线被破坏。
3. 版本策略：语义化版本；**不兼容变更必须大版本 + 双方评审**；RF 与 floorplan 各自锁定版本。
4. 变更流程：架构侧提案 → 影响面清单（两项目）→ 双方评审 → 新版本发布 → 各项目自行升级并跑全量验收。
