## 背景

本仓的幂等原先是**三层**（请求指纹 + 数据库唯一索引 + 业务唯一键），两处「先查后插」仍留有并发窗口：

1. **进件去重**（`application-service`）：受理前按「同一人 + 同一台车 + 窗口期」查在途申请，查不到才落库。
   两个并发请求（同一客户同一台车、不同 `Idempotency-Key`）可以同时查到「无重复」，各自落一条申请 → 双份申请。
   同幂等键并发另有 `uk_app_idempotency` 兜底，但**同键异内容**的并发会撞唯一索引 → 旧写法直接抛异常 → HTTP 500。
2. **回调幂等**（`external-api` → `title-release-service`）：DMZ 的 nonce 关只挡**同一 nonce 重放**；
   外部方「换 nonce 重推同一业务回执」时挡不住 → 回执重复落库、状态重复推进、闭环事件重复发出。

`AGENTS.md` §2 已定「唯一键幂等走 `ON CONFLICT` 原子语义」，但**唯一索引只能覆盖「键相同」的场景**：
业务唯一键（客户 + 车辆 + 窗口期）与「同一业务回执」都缺少一个跨实例的串行化手段。

被否掉的路线是「只靠数据库」：窗口期去重无法用唯一索引表达（时间窗不是索引语义），
而回执幂等若只靠「先查后插」，并发窗口依旧存在。

## 结论

1. **引入 Redisson 3.27.2**（`org.redisson:redisson`，父 pom 统一版本），作为**分布式锁**的唯一实现；
   不引 Spring Boot 的 Redis starter 自动装配，客户端由 `common/lock/RfLockConfig` 显式装配（精确装配纪律）。
2. **锁机制件放共享 `common`**（横切机制层）：端口 `DistributedLockManager` + 适配器 `RedissonLockManager`
   + 锁键命名 `LockKeys` + 装配 `RfLockConfig`；使用方（`application-service` / `title-release-service` /
   `external-api`）显式 `@Import` 并各自声明依赖（`optional` 不传递）。
3. **fail-closed**（用户裁定）：Redis 不可达 → 抛 `RF_LOCK_002`（503）拒绝写，**不降级放行**；
   抢锁等待超时 → 抛 `RF_LOCK_001`（409）按并发冲突拒绝。服务启动时 Redis 不可达则**启动失败**（fail-fast）。
4. **锁在事务提交后释放**：临界区在事务内执行时，用 `TransactionSynchronization#afterCompletion` 释放；
   否则「锁已释放、事务未提交」会让下一个请求查不到刚写的行——这正是先查后插竞态的成因。
5. **覆盖两条链**：
   - 进件：`application-service` 受理前按「客户 + 车辆」加锁，**锁内重查**去重窗口；
   - 回调：`external-api` 入站转发按「订单 + 回执号」加锁（拦并发重复转发），
     `title-release-service` 回执登记按同一业务键加锁（拦并发重复落库与状态推进）。
   两把锁**分域不共用**（`dmz-callback` / `registry-receipt`），否则 DMZ 持锁调下游会自死锁。
6. **锁不是正确性来源，最终权威仍是数据库**：
   - 进件：同幂等键并发由 `uk_app_idempotency` 兜底（写入改 `ON CONFLICT (idempotency_key) DO NOTHING`，
     冲突方按请求指纹判定「重放」或 `RF_CONFLICT_001`）；
   - 回调：新增 **V19** 迁移 `uk_receipt_order_authority_ref`（订单 + 权威 + 回执号唯一，
     `COALESCE(receipt_ref,'')` 表达式索引），写入走 `ON CONFLICT DO NOTHING`，
     冲突方幂等返回既有结果、不重复落库、不重复推进状态、不重复发事件。
7. **锁键不落明文业务标识**：键格式 `retail:lock:{用途}:{SHA-256 前 16 位十六进制}`，
   避免明文客户号 / 车辆识别码 / 回执号进入 Redis 监控与慢日志（`R08` 个人信息隔离）。

## 后果

- **正面**：并发重复进件与重复回调各有一道跨实例的闸；回调重复投递从「重复落库 + 重复发事件」变成幂等返回。
- **代价**：① 受保护写路径新增硬依赖 Redis——Redis 不可用即拒绝写（可用性换正确性，金融口径的取舍）；
  ② 父 pom 与三个服务 pom 新增依赖；③ 编排脚本新增 Redis 容器（`retail-finance-lock-redis`，宿主端口 6381）；
  ④ 新增一条 Flyway 迁移 V19（唯一索引；V18 已被 W-CACHE/W-RL 的「产品档位与还款计划快照」占用并执行，字节不动）。
- **边界**：锁只覆盖**本轮**已明确的两条链（进件、回调）；报送触发 / 日批 / DPD 快照等仍有并发窗口，
  但那些路径已有「唯一约束 + 条件更新」的原子抢占（`uk_batch_job_date` 等），不靠锁。
- **风险与对策**：Redis 单点 → 锁服务不可用即拒写（fail-closed），业务不产生错数据，只产生拒绝；
  锁租约过期 → 用看门狗续期（不设固定 lease），长事务不会中途失锁。

## 被拒选项与理由

| 选项 | 不选的理由 |
|---|---|
| 继续只用数据库唯一索引 | 时间窗去重无法用索引表达；回执「先查后插」仍有并发窗口 |
| 捕获唯一键异常再重读 | PostgreSQL 事务内一旦触发唯一键错误，整笔事务即被置为 aborted，无法继续读库 |
| 锁不可用时降级放行 | 金融写路径宁可拒绝错，不可放行错（`AGENTS.md` §8 fail-closed 纪律） |
| 锁不可用时降级为 JVM 本地锁 | 多实例部署下静默失去互斥，比直接失败更危险 |
| 引入 Spring Boot Redis starter 自动装配 | 与「精确装配」纪律冲突；自动装配会顺带引入连接池与 Lettuce，本仓只需锁 |
| 把锁当正确性来源（只加锁不加唯一索引） | 双一致性来源；锁一失效即出现重复写 |
| 用 Redis 做多级缓存 / 削峰 | 与本轮目标无关；缓存需实测依据，另行评估 |

## 权衡

- **可用性 vs 正确性**：本 ADR 选择「Redis 不可用即拒绝写」。代价是 Redis 故障期间受保护写路径不可用；
  收益是故障期间**不产生**重复申请、重复回执与重复事件——在金融账务里，重复写的代价远高于暂时拒写。
- **锁 + 索引双保险**：锁把并发窗口收敛到「一个请求」，唯一索引保证「即使锁失效也不重复写」。
  两者职责不同，不是同一件事做两遍。
- **锁粒度**：按业务键加锁（客户 + 车辆、订单 + 回执号），而不是全局锁——全局锁会把无关业务串成一条队列。
