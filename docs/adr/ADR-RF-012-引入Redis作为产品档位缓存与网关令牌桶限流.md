# ADR-RF-012：引入 Redis 作为产品档位缓存与网关令牌桶限流

## 状态

**Accepted**（2026-11-23，用户指示「完整落地 + Caffeine L1 + Redis L2 一起做」「补，Redis 令牌桶（引 Redis 依赖）」）
· 影响：`R00 §3.5 §6 §7`、`R02 §7`、`R06 §4.3 §6`、`R08 §5`、`AGENTS.md` §2 §4、`PROGRESS §2 §6`
· 取代范围：**仅取代 `ADR-RF-008` §4 的「不引入 Redis 作为缓存（起步）」条款**；
`ADR-RF-008` 的其余结论（本地附件、不引 MQ/Seata/对象存储）继续有效。
· **2026-11-24 修订**（用户指示「两套限流实现都合并，用一个配置开关选择用哪种」）：
新增第 12 条（限流实现双轨 + 模式开关）与第 13 条（边缘 Nginx 为可选部署形态），
并相应补充「变难」与「明确不做」。第 1~11 条的缓存与限流基线结论继续有效。

## 背景

- `ADR-RF-008` §4 预留了 Redis 的引入条件：**只做幂等去重与短时锁，绝不缓存账本/PII/审查结果**。
  本轮用户明确指示引入 Redis（用途为产品档位多级缓存 + 网关令牌桶限流），超出该预留范围，
  需一份新决策把**边界写死**，避免「什么都往 Redis 里塞」。
- **还款计划的利率原本是入参且不落库**：`core.repayment_plans` 只有 method / 期数 / 首期到期日，
  计划生成后**无法复现当时算法、无法重算对账**，客户争议「当时到底几息」时库里查不出来。
  产品档位配置化是硬需求（不只是"更好管理"）。
- 产品档位是典型的「**读多写少、变更低频、需要版本化审计**」的配置：
  放款计划生成时每次都要读档位参数，而配置一天可能只改一次。
- **网关此前没有任何流量保护**：只有 `RequestIdFilter`。外部回调、爬取、误重试可以直接打到业务服务。
- 本仓 Redis 与 floorplan **物理隔离**：独立容器、独立端口、独立键前缀（`PROGRESS §2` 登记）。

## 结论

1. **引入 Redis，用途白名单仅两类**：
   (a) **只读业务配置的分布式缓存 L2**（本轮仅产品档位目录）；
   (b) **网关令牌桶限流状态**。
2. **绝不缓存**：债权余额、核销流水、入金明细、个人信息、征信查询与报送结果、审查结论、
   法定书面文件内容。**这些的权威源永远是 PostgreSQL**，Redis 只存可随时重建的派生值。
3. **两级缓存**：L1 = Caffeine（JVM 内，短 TTL，`get(key, mappingFunction)` 单飞防击穿）；
   L2 = Redis（跨实例）。**主动失效为主、TTL 兜底**：配置写成功**提交后**删 L1+L2；
   删不掉则靠 L2 TTL（默认 60s）收敛。
4. **失效必须在事务提交后**（`CacheInvalidator`）：提交前失效会被并发回源把未提交的旧值又写回缓存，
   等于「刚改完还是旧值」。
5. **降级口径**：
   - 缓存：Redis 不可用 → **直读数据源**，正确性不受影响（缓存是优化，不是权威）；
   - 网关限流：**fail-open 放行**（限流是保护层，不是安全边界；真正的重复提交已被服务内幂等挡住），
     可配置切 fail-closed。
6. **产品档位必须版本化 + 生效区间 + 快照**：
   - `core.financial_products`：同码多版本（`product_code + product_version` 唯一），
     按「生效日 ≤ 业务日 < 失效日 且启用」选版；改配置 = **旧版本封口停用 + 新版本插入**（不原地覆盖，保住变更审计）。
   - `core.repayment_plans` 落 **快照三件套**：`product_code / product_version / rate_bp`。
     **改配置不得改历史计划**——只存引用不够（配置会改会下架）。
   - 参数合成优先级：**授信覆盖值 > 产品档位默认**，两者都进快照。
7. **Redis 锁不作为正确性来源**：唯一索引 + `ON CONFLICT` + 乐观锁 `version` 才是最终防线；
   分布式锁只做「减少无效冲突」的性能优化。**本轮不引入 Redisson**。
8. **令牌桶用 Lua 脚本原子扣减**：读令牌 → 计算 → 写回必须原子，否则并发请求会读到同一个令牌数并都放行。
   多实例共享 Redis 计数——本地计数会让实际放行量变成「单实例额度 × 实例数」，限流失效。
9. **限流键**：网关本阶段**不验签**（鉴权下沉各服务本地验签），拿不到可信主体，
   故用 Authorization 头的 **SHA-256 哈希**区分调用方（凭据本身不入 Redis 键），无头时退化为来源 IP。
   生产验签后应改用验签得到的主体 ID。
10. 限流响应沿用统一 `ApiResponse` 结构（`code/message/data/traceId/details`），
    错误码 `RF_GATEWAY_001`（429），带 `Retry-After`。
11. 本地端口登记 **6382**（6379 已被本机其他进程占用），容器 `retail-finance-redis`，
    **不持久化**（缓存可重建、限流状态丢了重算即可，落盘没有价值）。
12. **限流实现双轨，一个开关二选一**（2026-11-24 修订）：网关保留两套限流实现——
    (a) **Redis 令牌桶**（`RateLimitFilter`）：Lua 原子扣减、计数共享、**多副本下配额准确**，**缺省模式**；
    (b) **进程内令牌桶**（`InMemoryRateLimitFilter`）：零外部依赖、**单实例口径**
    （多副本时实际放行量 ≈ 单副本额度 × 副本数）。
    开关：**`retail.gateway.rate-limit.mode` = `redis` | `memory`**（缺省 `redis`）。
    **两套互斥装配**（两个 `@Configuration` 各带互补的 `@ConditionalOnProperty`），
    同一时刻只注册一个限流过滤器——**绝不叠加**，否则请求被双重限流、额度减半且难排查。
    参数前缀：redis 模式 `retail.gateway.rate-limit.*`；memory 模式 `retail.gateway.rate-limit.memory.*`。
    **为什么两套都留**：单实例部署 / 无 Redis 环境（开发机、边缘节点、灾备切换）需要零依赖兜底，
    多副本必须走 Redis；保留两套而不是删掉一套，是为了让切换**可回退**（切回 `redis` 即恢复分布式口径），
    且两套各自的验收脚本与运维口径都能保留。
    **代价**：两套实现都要维护；开关切错会静默降级成单实例口径——**切模式必须显式登记**（`PROGRESS §2`）。
13. **边缘 Nginx 是可选部署形态，不是部署单元**：入口 Nginx（**18076** 前置内部网关 / **18077** 前置外部 DMZ）
    按来源 IP 做**连接级泄洪**（`limit_req` 漏桶 + `limit_conn`），配置见 `nginx/nginx.conf`；
    它**不占 Java 部署位**，与网关层是**两层分工**（边缘泄洪、网关管业务配额），不是重复建设。
    网关层必须登记 Nginx 所在网段（`trusted-proxy-cidrs`），否则所有客户端会被算成同一个来源、共享同一个桶。

## 后果

**变容易**：产品参数可运营配置；计划可复现可审计（改配置不改历史）；网关有了入口流量保护；
缓存机制件（`common/cache`）可被其他服务复用。

**变难**：多一个运行时依赖（本地需起容器）；配置失效链路多一层（提交后钩子）；
Redis 成为新的故障点——已用「缓存降级直读 + 限流 fail-open」把影响面压到最小。
**变难（修订补充）**：限流有**两套实现**要维护，且必须靠**一个开关**互斥装配——
装配期一旦失效（两个条件同时命中）就会**双重限流**；故以 `RateLimitModeSwitchTest` 在装配期钉死互斥。

**明确不做**：不缓存任何账务 / PII / 审查结果；不引 Redisson；不把 Redis 当分布式锁的正确性来源；
不引 Spring Cache 抽象（版本化主动失效、不可变快照、可控降级三件语义它给不了）；
**不把两套限流实现同时装配**（叠加即双重限流）；不引入第三种限流实现。

## 被拒选项与理由

| 选项 | 理由 |
|---|---|
| 只用本地 Caffeine（不引 Redis） | 多实例缓存不一致，档位改版各实例生效时间不同；限流计数变成「单实例额度 × 实例数」→ 限流失效 |
| 用 Spring Cache `@Cacheable` | 拿不到「版本号主动失效 + 不可变快照 + 可控降级」；金融配置的失效语义必须显式写死 |
| 引入 Redisson 做分布式锁 | 锁不是正确性来源（唯一索引才是）；多一个客户端与故障点，收益只是省 CPU |
| 用 PostgreSQL 计数表做网关限流 | 每请求一次 DB 往返，网关自己成为热点；限流状态与业务库同故障域 |
| 只靠 TTL 失效缓存 | 改配置后 TTL 窗口内仍按旧利率放款 → 资损 |
| 提交前失效缓存 | 并发回源把未提交的旧值写回缓存，等于「改完还是旧值」 |
| 把档位费用一并放进产品表 | 费用属**合同条款**（法定书面文件承载），以合同侧口径为准；放进产品表会绕过合同口径 |

## 权衡

引入一个**轻量、无持久化**的中间件，换取「配置可运营 + 计划可复现 + 入口有流量保护」三项能力；
用「主动失效 + 提交后钩子 + 降级直读 + fail-open」把新增故障点的影响面压到最小。
仍然坚持本仓的第一原则：**钱的正确性只认 PostgreSQL，Redis 只存可随时重建的派生值。**
