## 背景

外部登记机关经 DMZ 回推解除回执。DMZ 侧有三道关（nonce 防重放、scope 校验、IP 白名单），
但 **nonce 只挡「同一 nonce 重放」**，挡不住外部方「换一个 nonce 重推同一业务回执」。
同一业务回执若重复入库，就会重复推进解押状态、重复发出闭环事件——证据链出现两条同源回执。

`wt/lock` 并行路线给出的方案是「分布式锁（Redisson）→ 锁内重查 → 唯一索引」三道闸。
按 `PROGRESS §9` 裁决**只取数据库层的幂等能力**：Redisson 不合入——
`ADR-RF-012` 已定「Redis 锁不作正确性来源」，且引入 Redisson 会给受保护写路径
新增一个硬依赖与一个失败模式（Redis 不可达即写不进去），收益不足以抵消。

## 结论

1. **唯一索引是正确性来源**：`core.registration_receipts` 上建表达式唯一索引
   `uk_receipt_order_authority_ref (release_order_id, authority, COALESCE(receipt_ref, ''))`，
   迁移 **V19**（V18 已执行，字节不动）。
2. **写入走 `ON CONFLICT DO NOTHING`**：冲突返回 0 行即「已存在」，**不捕获唯一键异常**
   （PostgreSQL 事务内一旦触发唯一键错误，整笔事务即被置为 aborted）。
3. **应用层两道闸**：① 写入前查既有回执（重放判定，直接返回既有结果）；
   ② 写入返回 0 行（并发命中唯一索引）→ 幂等返回，不推进状态、不发事件。
4. **~~不引入分布式锁~~（2026-11-24 按用户指令修订，详见 §状态 的修订注）**：
   原裁决为「不新增 Redisson 依赖、不新增 `common/lock` 机制件；`DistributedLockManager` 端口与进程内实现本轮不并入」；
   现**改为引入**，落 `ADR-RF-015`——锁只收敛并发窗口，**唯一索引仍是正确性来源**（本 ADR 结论 1–3 不变）。
5. **权威写者仍是 title-release-service**：幂等判定与唯一索引都落在回执的权威写者侧；
   DMZ 只做验签与转发，不承担幂等职责。
6. **口径登记**：迁移号段占用见 `R06 §6` 与 `PROGRESS §2`；因 V19 被本 ADR 占用，
   `R06 §3.2` 的 G-DB-7 审计写入授权调整**顺延到 V20**（**后续修订 2026-11-24：V20 已被 MQ 密文信封通道占用，
   G-DB-7 实际落 V21**，见 `R06 §6` / `PROGRESS §2`）。

## 后果

- **正面**：外部方重推同一回执不再产生第二条回执、不重复推进解押状态、不重复发闭环事件；
  实现与本仓既有「唯一键幂等走 `ON CONFLICT`」口径一致，**不新增中间件**。
- **代价**：并发窗口内两个线程可能同时通过「写入前查」，此时靠唯一索引收敛为一条——
  即「先查」只是快路径，**唯一索引才是权威**。
- **不解决**：不解决「外部方换回执号重推」（那是新业务回执，按新回执登记，语义正确）。
- **后续**：`R06 §3.2` 的 G-DB-7 审计写入授权调整迁移改用 V20（**后续修订 2026-11-24：V20 已被 MQ 占用，
  G-DB-7 实际落 V21**）。
