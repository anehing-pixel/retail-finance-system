# ADR-RF-013：回调幂等——以数据库唯一索引为权威，不引入分布式锁

> **一句话决策**：外部回执重复推送时，用「表达式唯一索引 + `ON CONFLICT DO NOTHING`」做幂等，
> 唯一索引是正确性来源；2026-11-24 起按 `ADR-RF-015` 增加 Redisson 锁，但锁只收敛并发窗口，
> 不取代唯一索引。

## 背景

外部登记机关经 DMZ 回推解除回执。DMZ 侧有三道前置校验（nonce 防重放、scope 校验、IP 白名单），
但 **nonce 只挡「同一 nonce 重放」**，挡不住外部方「换一个 nonce 重推同一业务回执」。
同一业务回执若重复入库，就会重复推进解押状态、重复发出闭环事件——证据链出现两条同源回执。

并行路线 `wt/lock` 给出的方案是「分布式锁（Redisson）→ 锁内重查 → 唯一索引」三道闸。
本 ADR 初版裁决只取数据库层的幂等能力：`ADR-RF-012` 已定「Redis 锁不作正确性来源」，
且引入 Redisson 会给受保护写路径新增一个硬依赖与一个失败模式（Redis 不可达即写不进去），
收益不足以抵消。2026-11-24 用户指令改为同时引入锁，但保留「唯一索引兜底」的结论。

## 结论

1. **唯一索引是正确性来源**：`core.registration_receipts` 上建表达式唯一索引
   `uk_receipt_order_authority_ref (release_order_id, authority, COALESCE(receipt_ref, ''))`，
   迁移 **V19**（V18 已执行，字节不动）。
2. **写入走 `ON CONFLICT DO NOTHING`**：冲突返回 0 行即「已存在」，**不捕获唯一键异常**
   （PostgreSQL 事务内一旦触发唯一键错误，整笔事务即被置为 aborted）。
3. **应用层两道闸**：
   1. 写入前查既有回执（重放判定，直接返回既有结果）；
   2. 写入返回 0 行（并发命中唯一索引）→ 幂等返回，不推进状态、不发事件。
4. **~~不引入分布式锁~~（2026-11-24 按用户指令修订）**：
   原裁决为「不新增 Redisson 依赖、不新增 `common/lock` 机制件」；
   现改为引入，落 `ADR-RF-015`——锁只收敛并发窗口，**唯一索引仍是正确性来源**（结论 1–3 不变）。
5. **权威写者仍是 `title-release-service`**：幂等判定与唯一索引都落在回执的权威写者侧；
   DMZ 只做验签与转发，不承担幂等职责。
6. **口径登记**：迁移号段占用见 [R06 §6](../docs/R06-数据库设计.md) 与 [PROGRESS §2](../PROGRESS.md)；
   G-DB-7 审计写入授权调整最终落 **V21**（V20 已被 MQ 密文信封通道占用）。

## 后果

### 正面

- 外部方重推同一回执不再产生第二条回执、不重复推进解押状态、不重复发闭环事件；
- 与仓库既有「唯一键幂等走 `ON CONFLICT`」口径一致，不新增中间件即可获得正确性；
- 2026-11-24 后增加锁，减少并发窗口内的无效冲突与唯一键竞争。

### 代价

- 并发窗口内两个线程可能同时通过「写入前查」，此时靠唯一索引收敛为一条——
  「先查」只是快路径，**唯一索引才是权威**；
- 引入 Redisson 后，Redis 不可达 → 受保护写路径 fail-closed 拒写（503），可用性代价已确认。

### 不解决

- 不解决「外部方换回执号重推」——那是新业务回执，按新回执登记，语义正确。

## 被拒选项与理由

| 选项 | 理由 |
|---|---|
| 只靠应用层「先查后插」 | 并发窗口内两个请求可同时查到「不存在」，各写一条，幂等失效 |
| 捕获唯一键异常再重读 | PostgreSQL 事务内唯一键错误会使整笔事务 aborted，无法继续读库 |
| 只用 Redisson 锁、不建唯一索引 | 锁失效或 Redis 故障时没有最终防线；锁不是正确性来源（`ADR-RF-012`） |
| 在 DMZ 做幂等 | DMZ 只做验签与转发，不承担业务幂等；权威写者在 `title-release-service` |

## 权衡

放弃「单一机制解决所有并发」的简洁性，换取**数据库层最终一致的正确性**：
唯一索引负责「键相同」的重复，锁负责减少并发窗口中的无效冲突。两套机制叠加，
但职责不重叠——锁是性能优化，索引是正确性来源。
