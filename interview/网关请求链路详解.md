# 网关请求链路详解（api-gateway / external-api）

> **用途**：把本仓库「消费者/门户请求怎么进网关、网关怎么处理、怎么分发到业务服务、traceId 怎么贯穿」讲清楚，可当作架构讲解稿或面试追问底稿。
>
> **事实源**：当前 master 代码（2026-11-25 阅读）。本文是**代码解读**，不构成新的设计口径；与 `docs/R02`、`docs/R07`、`docs/R09`、`docs/adr/ADR-RF-*` 冲突时，以设计文档为准。
>
> **边界**：系统未上线、无生产流量；文中端口、进程数、命令均以本仓库现有配置为准。

---

## 0. 一张图看全链路

```
消费者 / 门户（浏览器、App、合作门户）
        │  HTTPS /api/**
        ▼
[可选] 边缘 Nginx :18076              ← 默认不启用，nginx/nginx.conf
        │  透传 X-Real-IP / X-Forwarded-For / X-Request-Id
        ▼
api-gateway :18081                    ← Spring Cloud Gateway（WebFlux + Reactor Netty）
        │  路径路由 + X-Request-Id + 令牌桶限流 + CORS
        ▼
业务服务 8090–8099                    ← Spring MVC（Servlet/Tomcat），鉴权与业务在这里
        └─ retail-core / auth / customer / application / underwriting /
           bureau / contract / title-release / servicing / recon

外部机构（DMS / 征信 / 银行 / eKYC / 登记机关）
        │  签名请求 /external/**
        ▼
external-api :18091（DMZ）            ← per-partner HMAC + nonce + scope + 调用留痕
        │  以系统服务身份转发内部命令
        ▼
业务服务（例如 title-release :8097）
```

一句话：**`api-gateway` 是内部人面向的流量入口，`external-api` 是外部机构面向的 DMZ 集成边界，两者不是同类网关，也不是主备关系。**

## 1. 两个入口：api-gateway 与 external-api 的区别

### 1.1 对比表

| 维度 | `api-gateway` :18081 | `external-api` :18091（DMZ） |
|---|---|---|
| 面向谁 | 员工运营台、客户 BFF（人） | DMS、征信机构、银行、eKYC、登记机关（机构系统） |
| 鉴权模型 | 网关**不验签**；JWT 由下游各服务验（员工/客户双主体） | **per-partner HMAC 签名** + 时间戳 + nonce + scope + partner 状态 + IP 白名单 |
| 技术栈 | WebFlux + Reactor Netty，**无数据库** | Servlet/Tomcat + MyBatis + PostgreSQL |
| 数据权限 | 不连库 | 只授 `retail_dmz_rw`，仅 `integration` schema，**不授 `core` / `pii`** |
| 核心职责 | 路径切流、`X-Request-Id`、令牌桶限流、CORS | 验签、防重放、scope 校验、`integration.call_logs` 留痕、外部 DTO → 内部命令、转发 |
| 状态 | 无状态，可水平扩展 | 有状态：`integration.nonces`、`integration.call_logs`、partner 档案 |
| 当前端点 | `/api/**` 转发到 10 个服务 | `/external/health`、`/external/echo`、`/external/echo/canonical`、`/external/registry/receipts` |
| 限流 | 令牌桶按路径配额 | 进程内不限流；入站洪峰由边缘 Nginx 按来源 IP 泄洪（`R07 §7`） |
| 暴露面 | 内部网络 / 边缘 Nginx 之后 | 面向前置合作方或公网 |

### 1.2 为什么不用一个网关

`docs/R07 §2.1` 的原文口径：

> 两个入口**鉴权模型完全不同，不得混用**；在同一应用里加 `/external/**` 路径，网络隔离形同虚设。

具体原因：

1. **鉴权模型不能混**：一个是用户 JWT（员工/客户双主体），一个是合作方 HMAC 签名。放在同一个进程里，任何一条代码路径都可能被错误的身份类型触达；URL 前缀不构成网络隔离。
2. **最小权限与爆炸半径**：DMZ 必须暴露给外部，必须假设它可能被攻破。它只拿 `integration` schema 的权限，拿不到核心账务和个人信息；内部网关则连数据库都不连。
3. **状态与依赖不同**：DMZ 需要持久化 nonce、调用流水、partner 凭据，还要加分布式锁保证回执幂等；网关必须保持无状态、低依赖、可随意扩副本。
4. **流量性质不同**：外部回调是机构级、突发、逐笔可审计；内部入口是用户请求，按路径段做配额即可。
5. **暴露面不同**：18091 面向外部，18081 只在内部网络或边缘代理之后。

### 1.3 external-api 当前实际做什么

- `/external/health`：免签健康自证；
- `/external/echo`：签名回显自证，走 `DmzGatekeeper` 校验并落 `integration.call_logs`；
- `/external/echo/canonical`：冒烟复算规范化串的辅助端点；
- `/external/registry/receipts`：登记机关回执入站。链路：

```
登记机关 → DMZ 三关（时间戳 → nonce → 签名 → 状态/scope/IP）
         → 分布式锁（订单 + 回执号，ADR-RF-015）
         → 以系统服务身份转发 title-release
           POST /api/release-orders/{id}/receipts
         → 失败不重试，保留上游响应语义
```

DMZ 的校验顺序在 `DmzGatekeeper` 里固定，不可调换：partner 已登记 → 时间戳 ±300s → nonce 防重放 → 签名常量时间比较 → partner 状态 → scope → IP 白名单。无论成功失败都写 `integration.call_logs`。

## 2. 消费者 / 门户的请求怎么进 18081

### 2.1 设计/生产形态

```
消费者 / 门户
   │ HTTPS
   ▼
[可选] 边缘 Nginx :18076
   │ HTTP
   ▼
api-gateway :18081
```

- 边缘 Nginx 是**可选部署形态件**，不是 12 个部署单元之一，默认不启用；
- 不启用边缘层时，门户直接连 18081；
- 外部机构流量**不经过 18081**，走 `external-api:18091` 的 `/external/**`。

### 2.2 本地验证形态

`frontend/serve.py` 在 18082 提供静态页 + 同源反向代理（仅本地验证，不是部署单元）：

| 前缀 | 目标 | 用途 |
|---|---|---|
| `/gw/**` | `http://127.0.0.1:18081` | 员工运营台主链路（所有 `/gw/api/...` 请求） |
| `/svc/**` | `http://127.0.0.1:8098` | servicing 直连旁路（本地测试口径） |
| `/cust/**` | `http://127.0.0.1:8092` | customer 直连旁路（本地测试口径） |

消费者登录也走网关：`POST /gw/api/auth/customer/login`。客户自助查询在本地页面上走 `/cust/api/customer-self/me` 直连；网关的 customer 路由段已经登记 `/api/customer-self/**`，生产形态应走 `/gw/api/customer-self/me`。

### 2.3 请求携带什么

- `Authorization: Bearer <JWT>`：员工 token 或客户 token，两者 iss/aud/密钥分离（`ADR-RF-004`）；
- `Content-Type: application/json`；
- 写接口 `Idempotency-Key`；
- 可选 `X-Request-Id`（没有则由边缘 Nginx 或网关生成）。

## 3. 边缘 Nginx 怎么把请求交给 18081

### 3.1 `proxy_pass` 是 TCP + HTTP 转发

`nginx/nginx.conf`：

```nginx
upstream retail_gateway {
    server 127.0.0.1:18081;     # nginx.conf:51-54
    keepalive 64;
}

server {
    listen 18076;
    location / {
        limit_req  zone=rf_edge_ip burst=100 nodelay;
        limit_conn rf_edge_conn 50;
        proxy_set_header Host            $host;
        proxy_set_header X-Real-IP       $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Request-Id    $request_id;
        proxy_pass http://retail_gateway;
    }
}
```

Nginx 的工作：**终止客户端连接 → 向 `127.0.0.1:18081` 新建或复用一条 TCP 连接 → 重新发一个 HTTP 请求**。网关不知道也不关心对面是不是 Nginx；对 18081 来说就是普通 HTTP 请求。

### 3.2 `X-Request-Id` 的来源

- 边缘启用时：Nginx 用 `$request_id` 生成并写入头，Nginx 访问日志也打印同一个值；
- 网关 `RequestIdFilter` 的规则是「入站有则透传、无则生成 UUID」，所以收到 Nginx 的 ID 就沿用；
- 边缘未启用时：门户可自带，或由网关生成。

### 3.3 keepalive 细节

`upstream keepalive 64` + `proxy_set_header Connection ""` 表示 Nginx 会复用已建立的 TCP 连接。第一条请求触发 `accept`，后续请求多数直接落在已有连接上被读取，不再触发接受新连接。

### 3.4 可信代理与限流

`X-Forwarded-For` 只是请求头，网关默认**不采信**。启用边缘层时必须把 Nginx 网段登记到：

- `retail.gateway.rate-limit.trusted-proxy-cidrs`（redis 模式）；
- `retail.gateway.rate-limit.memory.trusted-proxy-cidrs`（memory 模式）。

否则网关看到的来源全是 Nginx 自己，所有客户端共用一个限流桶。

## 4. 18081 是怎么被接住的（Spring Boot + Netty）

### 4.1 没有 XML，也没有手写 Netty

`gateway/src/main` 下没有 XML、没有 `web.xml`，也没有任何创建 `HttpServer` 的代码。监听 18081 完全由 **Spring Boot 响应式内嵌服务器自动配置**完成：

- 依赖链：`spring-cloud-starter-gateway` → `spring-boot-starter-webflux` → `reactor-netty-http`；
- 没有 `spring-boot-starter-web`，所以 WebApplicationType 判定为 **REACTIVE**，不会起 Tomcat；
- `server.port: 18081` 写在 `gateway/src/main/resources/application.yml:2`。

### 4.2 可执行 jar 与启动入口

打包时 `spring-boot-maven-plugin` 生成可执行 fat jar：

```
Main-Class:  org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.company.retail.gateway.GatewayApplication
```

`BOOT-INF/lib/` 内包含 `spring-cloud-gateway-server`、`spring-webflux`、`reactor-netty-http` 等。

`run-microservices.sh` 执行 `java -jar ...`：`JarLauncher` 建立 `LaunchedURLClassLoader`，加载 `BOOT-INF/classes` 与 `BOOT-INF/lib/*.jar`，再调用 `Start-Class` 的 `main`。**Maven 只在构建期把 jar 打进包，运行期是 `JarLauncher` + `SpringApplication` 决定装配什么。**

### 4.3 启动时序

```
SpringApplication.run(GatewayApplication)
 ├─ 推断 WebApplicationType = REACTIVE
 ├─ 创建 AnnotationConfigReactiveWebApplicationContext
 ├─ refresh()
 │   ├─ 读取各 jar 的
 │   │   META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
 │   ├─ 条件过滤：
 │   │   @ConditionalOnWebApplication(REACTIVE)
 │   │   @ConditionalOnClass(HttpServer.class)
 │   │   @ConditionalOnMissingBean(ReactiveWebServerFactory.class)
 │   └─ 创建 NettyReactiveWebServerFactory
 └─ onRefresh() → createWebServer()
     → getWebServer(HttpHandler)
     → HttpServer.create().port(18081).handle(ReactorHttpHandlerAdapter)
     → NettyWebServer.start() → bindNow()
```

其中 `HttpHandler` 是 WebFlux 把 `DispatcherHandler` + WebFilter 链包出来的处理器；Spring Cloud Gateway 只是这个处理器里的路由与过滤器实现。

### 4.4 Netty 连接级做了什么

1. Nginx `connect(127.0.0.1:18081)`；
2. Reactor Netty acceptor 线程在 selector 上收到 `OP_ACCEPT`，创建子 `NioSocketChannel`；
3. 该连接挂上 HTTP pipeline：`HttpServerCodec`（HTTP 编解码）、流量统计、Reactor Netty 桥接；
4. 请求完整后，`ReactorHttpHandlerAdapter` 把 `HttpServerRequest` 适配成 Spring 的 `ServerHttpRequest`，构造 `ServerWebExchange`；
5. `DispatcherHandler` → SCG 的 `RoutePredicateHandlerMapping` → `FilteringWebHandler`；
6. 响应原路返回：下游响应 → 过滤器链反向 → `ReactorHttpHandlerAdapter` 写回 Netty Channel → Nginx → 客户端。

默认参数：1 个 acceptor 线程、worker 线程数约等于 CPU 核数（最少 4），非阻塞；项目没有自定义 `server.netty.*`，全部走 Boot 默认值。

> 本机若注入了 `SERVER__PORT` 环境变量，它会覆盖 `server.port`。启动脚本统一用 `env -u SERVER__PORT` 规避（`AGENTS.md §4`）。

## 5. 过滤器链：GlobalFilter 与 Ordered

### 5.1 不是 Servlet Filter

网关是 WebFlux/Netty 栈，`jakarta.servlet.Filter` / `OncePerRequestFilter` 在这里不生效。`RequestIdFilter` 实现的是 Spring Cloud Gateway 的 `GlobalFilter`：

```java
public class RequestIdFilter implements GlobalFilter, Ordered {
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String requestId = exchange.getRequest().getHeaders().getFirst(HEADER);
        if (requestId == null || requestId.isBlank()) {
            requestId = UUID.randomUUID().toString();
        }
        ServerWebExchange mutated = exchange.mutate()
                .request(r -> r.headers(h -> h.set(HEADER, requestId)))
                .build();
        exchange.getResponse().getHeaders().set(HEADER, requestId);
        return chain.filter(mutated);
    }

    public int getOrder() { return -100; }
}
```

它只做三件事：补 `X-Request-Id`、写请求头、回显响应头，然后无条件放行。**不校验、不拦截、不做业务决定。**

### 5.2 哪些 GlobalFilter 会进链

不是「实现了就自动进链」，而是：**当前应用上下文里存在 `GlobalFilter` 类型的 bean**。

Spring Cloud Gateway 自动装配：

```java
@Bean
@ConditionalOnMissingBean
public FilteringWebHandler filteringWebHandler(List<GlobalFilter> globalFilters) {
    return new FilteringWebHandler(globalFilters);
}
```

`List<GlobalFilter>` 按类型注入所有 bean。注册方式可以是：

- `@Component` 且在组件扫描范围内（网关扫描 `com.company.retail.gateway`）；
- `@Bean` 工厂方法；
- `@Import` 导入的配置类中的 `@Bean`。

条件不满足或不是 bean 的类不会进链。反例：`RateLimitFilter` / `InMemoryRateLimitFilter` **没有 `@Component`**，而是由条件配置类里的 `@Bean` 注册。

### 5.3 顺序由 `getOrder()` 决定

`FilteringWebHandler` 启动时把每个 `GlobalFilter` 包装成 `GatewayFilter`，并记录顺序；每个请求命中路由后，把全局过滤器与路由级过滤器合并，按 `AnnotationAwareOrderComparator` 排序：

```java
if (filter instanceof Ordered) {
    return new OrderedGatewayFilter(adapter, ((Ordered) filter).getOrder());
}
Order order = AnnotationUtils.findAnnotation(filter.getClass(), Order.class);
if (order != null) {
    return new OrderedGatewayFilter(adapter, order.value());
}
return adapter;   // 没有排序信息 → 排序时视为最低优先级
```

- 值越小越先执行；
- 不实现 `Ordered` 可以用 `@Order`；
- 都没有则排最后；
- 值相同则保持原列表顺序（稳定排序）。

本项目顺序：

| 过滤器 | order | 作用 |
|---|---|---|
| `RequestIdFilter` | -100 | 补请求号 |
| `RateLimitFilter`（或 memory 版） | -90 | 限流 |
| `NettyWriteResponseFilter`（内置） | -1 | 请求阶段占位，响应回来时写客户端 |
| `RouteToRequestUrlFilter`（内置） | 10000 | 拼目标 URL |
| `ReactiveLoadBalancerClientFilter`（内置） | 10150 | `lb://` 选实例 |
| `NettyRoutingFilter`（内置） | `Integer.MAX_VALUE` | 发出 HTTP 请求 |

**响应阶段是反向的**：过滤器里 `chain.filter(exchange)` 之后的逻辑按倒序执行。

### 5.4 限流器为什么没有 `@Component`

两套限流实现必须互斥：

- `RateLimitConfig`：`@ConditionalOnProperty(mode=redis, matchIfMissing=true)`，`@Bean RateLimitFilter`；
- `InMemoryRateLimitConfig`：`@ConditionalOnProperty(mode=memory)`，`@Bean InMemoryRateLimitFilter`。

如果两个类都标 `@Component`，它们会无视 `mode` 永远同时成为 bean，链上同时挂两套限流器，等于双重限流。`RateLimitModeSwitchTest` 在装配期钉死「任意时刻只有一个限流过滤器」。

## 6. 网关怎么把请求分发到业务服务

### 6.1 路由选择

路由全部显式声明在 `gateway/application.yml:32-77`，只使用 `Path` 谓词，首个命中即停，精确路由在前、`/api/**` 兜底到 `retail-core`：

| 路由 id | 路径谓词 | 目标 |
|---|---|---|
| auth | `/api/auth/**` | auth-service :8091 |
| customer | `/api/customers/**`、`/api/identity-verifications/**`、`/api/consents/**`、`/api/pii/**`、`/api/customer-self/**` | customer-service :8092 |
| application | `/api/applications/**`、`/api/dealer-partners/**` | application-service :8093 |
| underwriting | `/api/underwriting/**`、`/api/rules/**` | underwriting-service :8094 |
| bureau | `/api/credit-inquiries/**`、`/api/bureau-reports/**`、`/api/bureau-disputes/**` | bureau-service :8095 |
| contract | `/api/contracts/**` | contract-service :8096 |
| title-release | `/api/title-retentions/**`、`/api/release-orders/**` | title-release-service :8097 |
| servicing | `/api/collection-cases/**`、`/api/dpd-snapshots/**`、`/api/jobs/dpd-snapshot` | servicing-service :8098 |
| recon | `/api/recon/**` | recon-service :8099 |
| core | `/api/**`（兜底） | retail-core :8090 |

URI 双模：`${ROUTE_*:lb://服务名}`。生产用 Nacos + Spring Cloud LoadBalancer，本地用 `ROUTE_*` 覆盖成 `http://127.0.0.1:端口`。

`spring.cloud.gateway.discovery.locator.enabled=false` 只是禁止「按服务名自动生成路由」，不影响 `lb://` 查询实例。

### 6.2 四个内置分发过滤器

**① `RouteToRequestUrlFilter`（10000）**

把原始请求的 path/query 与路由的 scheme/host/port 合并：

```
请求 /api/customers/123?x=1
路由 uri: lb://customer-service
→ lb://customer-service/api/customers/123?x=1
```

本项目没有配置 `StripPrefix`，路径原样保留，下游 controller 收到的就是 `/api/...` 全路径。

**② `ReactiveLoadBalancerClientFilter`（10150）**

仅对 `lb://` 生效：

1. 取 `serviceId`；
2. 通过 Spring Cloud LoadBalancer + DiscoveryClient（生产是 Nacos）选一个实例；
3. 重写为 `http://ip:port/api/...`；
4. 找不到实例 → `NotFoundException`（默认 503）。

本地 `ROUTE_*` 是 `http://`，scheme 不是 `lb`，这个过滤器直接跳过。

**③ `NettyRoutingFilter`（`LOWEST_PRECEDENCE`）**

真正发出请求的环节，使用 Reactor Netty `HttpClient`：

- method、URI、headers、body 原样代理；
- `Authorization`、`Idempotency-Key`、`X-Request-Id` 等透传；
- hop-by-hop 头（`Connection`、`Transfer-Encoding` 等）被过滤掉；
- 下游响应状态码与响应头写入 exchange；
- 连接由 Reactor Netty 连接池管理。

**④ `NettyWriteResponseFilter`（-1）**

请求阶段只负责 `chain.filter()` 下传；响应回来时把下游状态码、响应头、响应体写回客户端。网关**不做响应改写**，`ApiResponse<T>` 原样透出。

### 6.3 一个完整例子

`GET /api/customers/123`：

```
1. 路由匹配：/api/customers/** → id=customer, uri=lb://customer-service
2. RouteToRequestUrl   → lb://customer-service/api/customers/123
3. LoadBalancer        → http://10.0.0.12:8092/api/customers/123
4. Netty HttpClient    → GET http://10.0.0.12:8092/api/customers/123
5. customer-service    → TraceIdFilter → JWT 拦截器 → Controller
6. 响应 JSON 沿链返回 → NettyWriteResponseFilter → 客户端
```

### 6.4 异常行为

- 路由没匹配 → 404，过滤器链不执行；
- `lb://` 找不到实例 → 默认 503；
- 下游连接拒绝/超时 → Netty 异常向上抛，网关返回错误；
- 本项目没有配置重试、熔断、自定义下游超时，是 SCG 默认行为。

## 7. 令牌桶限流

### 7.1 概念

令牌桶按「平均速率放行 + 允许一定突发」工作：

- 桶最多存 `capacity` 个令牌；
- 每秒补充 `rate` 个令牌；
- 每个请求消耗 1 个令牌；
- 有令牌 → 放行；桶空 → 429。

长期平均速率 ≤ `rate`；`capacity` 决定瞬时突发上限。

### 7.2 `replenish-rate` 与 `burst-capacity`

以进件路径为例：

```yaml
- path: /api/applications/**
  replenish-rate: 20       # 每秒补 20 个令牌 = 长期平均 20 请求/秒
  burst-capacity: 40       # 桶最多 40 个令牌 = 最多瞬时突发 40 个请求
```

- 客户端空闲后桶可攒满 40 个，来一波 40 个请求全部放行；
- 之后持续 30 请求/秒时，每秒只补 20 个，超出的 429；
- 令牌可以是小数，按毫秒补充；
- 每个规则 × 每个客户端各自一个桶。

### 7.3 按路径给不同配额

`gateway/application.yml:96-112`：

| 路径模式 | replenish-rate | burst-capacity | 意图 |
|---|---|---|---|
| `/api/applications/**` | 20/s | 40 | 进件收紧，防外部刷单 |
| `/api/credit-inquiries/**` | 10/s | 20 | 征信查询最严：外部成本高 + 合规敏感 |
| `/api/rate-limit-probe/**` | 1/s | 2 | 冒烟探针，极低额度 |
| `/api/**` | 500/s | 1000 | 全局兜底 |

**最具体优先**：`RateLimitRuleMatcher` 用 `AntPathMatcher` 匹配所有规则，取 pattern 最长的一条，不是按列表顺序。没有命中任何规则 → 直接放行。

### 7.4 Redis 模式（默认）

- `RateLimitFilter`（order -90）在路由转发前执行；
- 键：`rf:rl:{规则路径}:{客户端指纹}`；
- 客户端指纹：优先 `"a:" + SHA-256(Authorization)`，无 Authorization 时退化为 `"ip:" + IP`；
- Redis + Lua 原子扣减：读 tokens/ts → 按经过时间补充 → 不足则拒绝 → 写回并设置 TTL；
- Redis 不可用默认 **fail-closed → 503**；仅本地开发可显式 `fail-open`；
- 告警日志 `ALERT_RATE_LIMIT_REDIS_UNAVAILABLE` 按实例 10s 节流，不记 IP / Authorization；
- 超限响应：429 + `Retry-After: 1` + 统一结构：

```json
{
  "code": "RF_GATEWAY_001",
  "message": "请求过于频繁，请稍后重试",
  "data": null,
  "traceId": "...",
  "details": { "path": "/api/applications/..." }
}
```

### 7.5 进程内模式（可选）

- `InMemoryRateLimitFilter`，`mode=memory` 时装配；
- 键：路由段 + 客户端 IP；
- 桶在进程内存，限流是**单实例口径**：多副本时实际总放行量 ≈ 单副本额度 × 副本数；
- 响应额外带 `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`、`Retry-After`；
- `RateLimitRegistry` 有 `maxTrackedKeys=50000` 与空闲 600s 回收，防止伪造来源撑爆内存；
- 默认前缀规则写在 `InMemoryRateLimitProperties` 代码里，不读 yml 的 `rules`。

### 7.6 客户端 IP 与可信代理

`ClientIpResolver` 的规则：

- 直连来源不在 `trusted-proxy-cidrs` 内 → 只认 TCP 直连地址，**忽略** `X-Forwarded-For`；
- 直连来源命中可信网段 → 采信 `X-Forwarded-For`，取链中第一个非可信地址；
- 转发头里非 IP 字面量（主机名等）一律忽略，避免 DNS 解析阻塞网关线程。

这是为了防止「换一个 `X-Forwarded-For` 就重置限流」。

## 8. `X-Request-Id` / traceId 贯穿

### 8.1 网关端

`RequestIdFilter`（order -100）：

- 入站有 `X-Request-Id` 则透传，没有则生成 UUID；
- 写回请求头，下游服务能读到；
- 设置响应头，客户端能看到；
- 不做校验，不拦截。

### 8.2 服务端 `common` 的 `TraceIdFilter`

它是 Servlet 过滤器（`OncePerRequestFilter`），**业务代码不会显式调用它**，由容器自动执行。

注册位置：

| 位置 | 方式 | URL 匹配 |
|---|---|---|
| 业务 10 个服务 | `common/.../RfSecurityConfig.java:110-117` 的 `FilterRegistrationBean` | `/api/*`、`/external/*`，order 1 |
| DMZ `external-api` | `external-api/.../ExternalApiConfig.java:35-41` | `/external/*`，order 1 |

业务服务启动类都 `@Import(RfSecurityConfig.class)`（如 `CoreServiceApplication.java:23`），因此该过滤器在每个服务的 Servlet 上下文里生效。DMZ 不导入 `RfSecurityConfig`（不用员工 JWT 拦截器），所以单独注册一份。

运行时：

```
Tomcat → FilterChain（order 1）
  → TraceIdFilter.doFilterInternal()
      ① 读 X-Request-Id，没有就生成 UUID
      ② MDC.put("traceId", id)
      ③ request.setAttribute("traceId", id)
      ④ response.setHeader("X-Request-Id", id)
      ⑤ chain.doFilter(...)
  → HandlerInterceptor（JWT 验签）
  → DispatcherServlet → Controller
  ← finally: MDC.remove("traceId")
```

过滤器在 Spring MVC 拦截器之前执行，所以即使 JWT 拦截器返回 401/403，响应头里也已经有 `X-Request-Id`。

### 8.3 谁消费 traceId

**① `ApiResponse.traceId`**

`RfSecurityConfig.traceId(attrs)` 从请求属性取值，几乎每个 controller 都用：

- `retail-core`：`LoanController`、`PaymentController`、`SettlementController`、`JobController`、`FinancialProductController`、`RepaymentPlanController`；
- `auth-service`：`AuthController`；
- `contract-service`：`ContractController`；
- `common/web/WhoamiSupport`（`/api/health` 回显）；
- 各服务的 `WebAuthSupport.traceId()` 包装。

**② 业务链路 / 审计 / outbox**

- `ApplicationController` 把 traceId 传给 `ApplicationService.submit(...)`，最终写入 outbox 载荷；
- `PaymentTxExecutor` 把 traceId 放进核销事件 payload；
- 数据库表普遍有 `trace_id` 列；
- DMZ 的 `DmzGatekeeper` 把 traceId 写进 `integration.call_logs`；
- `AuditWriter` 等审计写入带 traceId。

**③ Feign 跨服务透传**

`JwtPassthroughInterceptor` 从当前请求取 `Authorization` 和 `X-Request-Id`，自动加到 Feign 出站请求头；下游服务的 `TraceIdFilter` 读到同一个值继续用。

**④ MDC 与日志的现状**

`TraceIdFilter` 确实执行了 `MDC.put("traceId", ...)`，但本仓库没有配置 `logback-spring.xml`、`logging.pattern.correlation` 或 `%X{traceId}`；Spring Boot 3.2 默认的 `LOG_CORRELATION_PATTERN` 为空，所以默认控制台日志**不会**打印这个 traceId。

当前真正起作用的是：请求属性、响应头、outbox/DB 列、Feign 透传。若要让日志行也带 traceId，需要配置类似：

```yaml
logging:
  pattern:
    correlation: "[%X{traceId:-}] "
```

## 9. 鉴权边界（重要）

- **网关不验 JWT**（`gateway/pom.xml` 描述里写死：「本阶段不验签（鉴权下沉各服务）」）；
- 下游服务由 `common` 的 `RfSecurityConfig` 注册两个拦截器：
  - 员工侧：`/api/**`（排除客户自助前缀）；
  - 客户侧：`/api/customer-self/**`；
- 员工与客户使用不同的 issuer / audience / 密钥（`RETAIL_JWT_SECRET` / `RETAIL_CUSTOMER_JWT_SECRET`）；
- 外部合作方不是 JWT，是 HMAC 签名，只到 DMZ；
- 权限点由 `@RequirePermission` 与 `RolePermissions` 控制。

因此：**网关是流量入口，不是身份边界；身份边界在各服务。**

## 11. 常见误解

| 误解 | 实际 |
|---|---|
| 「Nginx 直接调用 `RequestIdFilter`」 | 不是。Nginx 只发 TCP/HTTP 请求；网关内部由 Netty/WebFlux 解码，再进过滤器链。 |
| 「网关会验 JWT / 做权限」 | 不验。鉴权在各服务，网关只做路由、请求号、限流、CORS。 |
| 「实现了 `GlobalFilter` 就自动生效」 | 必须是 Spring bean；`@Component` 或 `@Bean` 注册，且条件装配满足。 |
| 「`RateLimitFilter` 有 `@Component`」 | 没有。它由 `RateLimitConfig` 的 `@Bean` 注册，靠 `@ConditionalOnProperty` 与 memory 版互斥。 |
| 「`getOrder()` 只影响同类过滤器内部顺序」 | 不是。全局过滤器与路由级过滤器合并后统一排序。 |
| 「限流是每秒计数器」 | 不是。令牌桶有存量、允许突发；`replenish-rate` 是流速，`burst-capacity` 是桶大小。 |
| 「两个网关是主备/前后置」 | 不是。18081 面向内部人，18091 面向外部机构，鉴权模型与数据权限不同。 |
| 「traceId 会默认打印在日志里」 | 当前没有配置日志 pattern，MDC 里的值默认不打印；响应、DB、outbox、Feign 透传不受影响。 |
| 「网关直接调用下游 Java 方法」 | 不是。网关用 Netty HttpClient 发 HTTP 请求，与下游是进程边界。 |
