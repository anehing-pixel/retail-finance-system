## 1. 项目一句话定位

> **形态口径提醒**：本项目主形态是**个品分期（个别信用购买斡旋，《分期付款销售法》体系）**，
> 钱由信贩**代付给销售店**、消费者向信贩分期支付，担保是**所有权保留**（不是抵押、不是无担保信用贷），
> 额度基准为**个别支付能力预估额**；系统按**双形态并行**（个品分期 + 汽车贷款）建模。

面向 C 端个品分期（商品分期销售 + 所有权保留）的信贷核心系统：
覆盖进件 → 征信 → 授信 → 合同 → 放款 → 账务 → 贷后 → 解押的**全信贷生命周期**，
Spring Cloud 微服务架构，12 个部署单元，按持牌消费金融合规要求设计（同意门禁 / 三重放款门禁 /

## 4. 架构叙述主线（按此顺序讲，5 分钟讲完）

1. **领域建模先行**：先做 12 个限界上下文的领域发现与上下文映射（`R02 §5`），再定服务边界——
   服务拆分是领域建模的结果，不是起点。
2. **拆分判断原则**：担保物形态不同必拆（车辆抵押 vs 商品所有权保留），通道能力相似必合
   （征信报送、银行代付、送达都是通道层）。不谈"生命周期长短"这类模糊标准。
3. **中台复用画界**：复用"能力"（契约 jar、错误码、事件常量、征信通道适配器），
   不复用"数据和状态"——否则中台退化为分布式单体。落法 = 契约冻结（`w2-frozen`）+ 事件白名单。
4. **双形态并行**：业务裁决"双形态并行"（`ADR-RF-002` Accepted），用 4 个策略点承接形态差异，
   而不是等业务定死后硬编码；形态反转的逐项返工量已预先评估（`R11 §8`）——架构允许低成本返工。
5. **数据隔离渐进**：第一版共库不同 schema + 明确的演进触发器（冲突写入集 / QPS 阈值），
   不一步到位拆库；独立库实例、独立号段、独立密钥（三把 JWT secret 互不相同）先隔离。
6. **验收判据先行**：契约冻结后才能开并行窗口；每个工作包以"合后全量构建 + 走网关冒烟 + E2E"
   为放行判据，文档一致性由 15 项机器校验守门。

## 5. 高频追问 Q&A（每条都有真实实现兜底）

**Q1：Outbox 为什么不直接发消息？**
本地事务写业务表与写 outbox 表在同一事务内，保证"状态变更"与"事件产生"原子；后台调度投递，
失败落 `outbound_tasks` 人工补发兜底。17 类事件走白名单校验（EventPayloadGuard），防止
payload 字段漂移。直接发消息无法保证两者原子性，这是选型的根本原因。

**Q2：合规门禁为什么 fail-closed？**
金融场景里"放行错"的代价（无同意报送征信 = 合规事故）远大于"拒绝错"（可重试）。
门禁取不到同意证据时一律拒绝。真实教训：事件驱动报送在调度线程执行，无请求上下文，
透传认证 401 → 报文永远 DEAD；修复 = 机器场景签发 `svc-*` 服务 token（`ConsentGateFacade`），
用户场景仍零信任透传。这个缺陷是模拟器联调暴露的——单测 mock 了门禁，e2e 未覆盖该断言，
说明"集成盲区要靠真实对端暴露"。

**Q3：nonce 防重放怎么保证原子性？**
nonce 以数据库唯一约束原子写入（重复回放写不进 → 409），不做"先查后插"（有竞态窗口）。
完整三关：HMAC-SHA256 规范化串验签（401）→ nonce 防重放（409）→ scope + IP 白名单（403），
全部留痕 `call_logs`（append-only，只追加不修改）。

**Q4：为什么自研模拟器？**
外部机构调研签约是长周期日历依赖，不能阻塞开发。零依赖 Node 模拟器实现六向对端
（征信/银行代付/eKYC/DMS/送达/入金文件），把"等外部"变成"对模拟器验收"。回报是抓出
4 个真缺陷：PartnerRegistry 密钥硬编码只认测试机构、保留登记与兜底建单的并发竞态 409、
构造器歧义导致服务启动失败、GET 请求携带 null body 违反浏览器 fetch 规范（只有真实浏览器触发）。
外部机构真实接入时只换 URL，报文差异由双模适配器消化。

**Q5：数据库为什么不一步到位拆库？**
共库不同 schema 起步：事务边界内简单、跨域查询明确、迁移成本低；同时预登记演进触发器
（写入集冲突 / QPS 阈值），到点按域拆库。直接每域独立库，跨域一致性（对拍、核销）成本翻倍，
早期是纯负担。隔离性先用"独立实例 5435 + 独立号段 + 独立密钥"保障。

**Q6：万一业务形态反转（分期改车贷为主）怎么办？**
`R11 §8` 有逐项返工量评估：双形态并行 + 4 个策略点（形态差异收敛在 4 个注入点），
反转只动策略点配置与对应域服务，不动共享底座。核心观点：**业务线会反转，架构要允许低成本返工，
所以每个重大决策都写 ADR 留痕**。

**Q7：服务间调用怎么保证安全与合规？**
员工/客户双主体 JWT（两把独立密钥，伪造 token 401）；服务间走 Feign 契约门禁（代付前三门禁：
合同 / 审查（同意门禁由合规链路消费），任一不过 fail-closed）；DMZ 只暴露外部回调入口，过门禁后由系统服务 token
转发内部，外部调用方永远拿不到内部凭据。

**Q8：持久层为什么用 MyBatis 注解 SQL，不用 JPA、也不用 XML？**
①**不用 JPA**：金融账务要的是**锁语义与 SQL 的完全可控**（`SELECT ... FOR UPDATE` 行锁、`ON CONFLICT` 幂等、
精确相等的不容差对拍），JPA 的自动 flush 会让"同一事务内先写后读"的判断变得不可预期。
②**不用 XML、只用注解 SQL**：SQL 就写在 Mapper 方法上，一眼看清这条接口到底打了几条 SQL、锁在哪张表，
不用在 XML 与接口之间来回跳；Mapper 接口本身就是持久层的**端口契约**，业务层不感知持久化实现。
③**行映射显式化**：查询结果统一映射成 `Map<String,Object>`，再由共享的 `RowValues` 按列名取值——
`getLong` 遇 NULL 返 0、`getString` 遇 NULL 返 null 这类口径在映射层就锁死，不依赖 ORM 的隐式类型推断，
也不让枚举 / 字符串转换散落在几十个 RowMapper 里。
④**装配纪律**：每个服务 `@MapperScan` 显式列出**自己的** mapper 包，不做全包扫描；
共享 infrastructure 的 mapper 由共享配置类单独注册。
⑤迁移用 Flyway 版本化，**已执行迁移字节不可改**，任何结构调整都走新迁移，schema 与代码的差异可审计。

**可以主动讲的迁移经历**：本项目最初是手写 `JdbcTemplate` + `RowMapper`，后来统一迁到 MyBatis 注解 SQL。
迁移红线是**SQL 语义、方法签名、事务边界、对外接口一律不变**——具体做法：Mapper 一律返回 `Map` 结果 +
`RowValues` 显式取值（保住原 RowMapper 的 NULL 口径）；唯一键幂等统一走 `ON CONFLICT` 原子语义
（`ON CONFLICT DO NOTHING`，而不是"捕获唯一键异常再重读"——PostgreSQL 事务内一旦触发唯一键错误，
整笔事务即被置为 aborted，无法继续读库）；一级缓存显式降级为 STATEMENT 级，
对齐原来"每次读都落库"的读语义，避免同一事务内重复 SELECT 命中本地缓存旧行。

**Q9：为什么不引完整的 Spring Security？**
只要 `spring-security-crypto`（BCrypt 口令散列），过滤链自研：这套系统要**双主体**（员工 / 客户两把密钥）
与**零信任服务间调用**，标准过滤器链表达不了"主体类型在验签层强制"和"外部方只经 DMZ 入口"这两条，
自研拦截器反而更短、更可控。

**Q10：Spring 的 BOM 顺序为什么手动前置？**
父 pom 把 `spring-framework-bom`（6.1.15）声明在 `boot-dependencies` 之前——Maven BOM 取**先声明者**，
Boot 3.2.5 自带的 Spring Framework 6.1.6 没有 `HttpHeaders.headerSet()`，而 Gateway 4.1.6 需要它。
这类"版本解析顺序"坑不写进文档，下次升级 BOM 就会以编译失败的形式暴露。

**Q11：引了 MQ，为什么它不是一致性方案？**（决策依据 `ADR-RF-014`；`AGENTS.md` B-10/B-15）

这条要主动把边界讲清楚，否则听起来像「为了用 MQ 而用 MQ」。三层：

1. **一致性仍然只有 outbox**：状态变更与事件产生放在同一本地事务落库，MQ 在事务之外。
   MQ 只解决「消息传输」，没解决「状态与消息的原子性」——所以 outbox 一步没退，
   **不引 Seata / 分布式事务**（全局锁 + 回滚日志在金融账务上风险过高）。
2. **MQ 解决的是洪峰，不是语义**：引它的动机是三类慢动作会形成尖峰——
   外部机构调用（征信报送批量重试）、大文件落盘与哈希对拍、法定书面文件送达。
   这些动作改成「控制器封**密文信封**丢进队列、消费者解密后执行同一个 handler」，
   主链路只负责受理与入队，速率由消费侧限速。
3. **为什么是密文**：broker 的落盘行永久保留，明文个人信息一旦入队撤不回来——
   所以 MQ 上**只允许出现密文信封**（8 个顶层键白名单 + 明文 PII 键默认拒绝，
   密钥复用 PII 数据密钥，不新增密钥面）。这不是绕过「事件载荷禁个人信息」的红线，
   而是把它从「进程内」延伸到「跨进程」的受控做法。

**代价（主动说，显得诚实）**：多一套可靠性语义（重复 / 延迟 / 死信 / 消费幂等）、
多一个外部依赖要运维、信封密钥成为敏感项、异步路径下接口返回不再代表业务已完成。

**开关与演进**：MQ **默认关闭**，默认路径是同步的，行为与原来逐字一致；
开了才走异步链路，而且「同一 handler 两个入口」，不写两份业务逻辑。
单 broker 起步（还不建集群），后续再按吞吐拆分。

**Q12：本系统的利息是怎么算的？**

核心就一行：**期次利息 = floor(期初余额 × 月利率基点 ÷ 10000)**。

- **利率用基点表示**：`monthlyRateBp`（月利率基点），`200 = 2.0%/月`，整数入参、构造器校验非负；
- **全程整数日元**（`long`），不做浮点；只有等额本息的年金公式用 `BigDecimal` 算中间系数，
  量化（`RoundingMode.FLOOR`）后立刻落回整数——对应 `R00 §5`「金额一律 BIGINT 整数日元、禁止 double 参与金额」；
- **代码位置**：`retail-core` 的 `RepaymentScheduleGenerator.interestOf`，纯领域函数、零 Spring 依赖，可纯 JUnit 跑。

四种还款方式：

| 方式 | 本金路径 | 利息 | 尾差 |
|---|---|---|---|
| 一次性还本付息 | 全部本金 1 期 | floor(本金 × bp ÷ 10000) | 无 |
| 等额本息 | 年金定每期总额后逐期模拟 | 按期初余额递减 | 归末期 |
| 等额本金 | 本金均分 | 按期初余额递减 | 归末期 |
| 奖金还款 | 奖金月期次权重 ×2 按权重分摊 | 按期初余额递减 | 归末期 |

年金公式：`每期总额 = P × r × (1+r)^n ÷ ((1+r)^n − 1)`，用 `BigDecimal.valueOf(monthlyRateBp, 4)` 构造 r，
FLOOR 量化到整数日元。**利率为 0 时退化为均分**（`principal ÷ count`）——所以「36 期 0 息」在本系统是天然支持的一档参数，
不需要任何特殊分支。

**尾差归末期**是硬保证：末期本金加上余数，保证 `Σ principalDue == principal` 一分不差；
期次内 `amountDue == principalDue + interestDue` 自洽。两条都有单测覆盖
（`RepaymentScheduleGeneratorTest` 8 个用例，含「故意取不能整除的本金 2,000,003」的精度用例）。

**边界守卫**：等额本息逐期模拟时，若某期利息 > 每期总额（超短期限 / 超低额度），本金部分置 0（**本金后置**），
不产生负数金额；本金部分超过剩余余额时截断到余额。

**利息怎么落到账上**：生成计划与应计利息入账在**同一本地事务**——先 `SELECT ... FOR UPDATE` 悲观行锁取债权，
生成期次落 `schedule_items`，再把 `Σ interestDue` 一次性计入 `loans.interest_accrued` 与 `loans.balance`，
最后用乐观锁 `version` 兜底（并发冲突拒绝整笔，不做部分写入）。

**必须主动说明的口径**：本系统是**计划期一次性计提**（计划生成时把全期利息一次性入账），**没有逐日计息**。
日批调度器 `ScheduleDueRollupScheduler` 做的是期次到期状态推进（OPEN→DUE→OVERDUE）+ 批次抢占锁 + 执行留痕，
不是计息。逐日计提只在「短期周转 / 逾期罚息」这类产品形态下才需要，成本落在每日重算期次与幂等补偿上。

**Q13：为什么有四种还款方式？「奖金还款」是什么业务场景？**

三种通行形态（一次性还本付息 / 等额本息 / 等额本金）是行业惯例，可以直接讲。

**奖金还款**对应零售场景中客户在奖金月（收入集中发放期）集中还款的安排：命中奖金月的期次本金权重 ×2、其余权重 1，
按权重折算每期本金比例，尾差归末期（`R04` U-6）。注意**利息仍按递减余额计**——放宽的是还款节奏，不是利率，
客户没有拿到额外的利率优惠。这两点要讲清楚，否则容易被误解成「打折」。

**Q14：提前结清金额怎么算？为什么不是「剩余本金 + 剩余利息」？**

口径（`C-10` 裁决）：**提前结清金额 = 剩余本金 − 减免额 + 事务手续费**。

两条守卫：
1. 剩余本金 / 减免额 / 手续费必须为非负整数日元；
2. **减免额不得超过剩余本金**——否则结清金额会低于手续费，口径不成立；减免上限本身待法务核实，
   系统侧只做这两条守卫，不越界做效力判断。

**为什么未到期利息不进这个公式**：提前结清是「提前终止」，尚未发生的期次利息不再向客户收取，
所以它不进报价，而是在**同一本地事务内作为豁免冲销**。三段式落地：
1. 手续费计提（`settlement_fee` 增收）；
2. 结清入金核销——只覆盖实收本金部分（`报价 − 手续费 = 剩余本金 − 减免额`）；
3. 豁免记账：未到期利息豁免 + 折让本金豁免 + 未核销费用豁免 → 余额精确归零 → 债权终态 `EARLY_SETTLED`。

**正常结清不走这套**：正常结清是末回核销完成、余额已精确为 0，只做状态迁移，不产生减免与手续费。
审查拒绝 / 撤回 / 提前结清 / 正常结清是**四个不同的债权终态**，不能合并（`AGENTS.md` B-7）。

**Q15：一次入金怎么拆到期次上？为什么是这个顺序？**

顺序：**费用 → 按期次顺序（`period_no` 升序）逐期，期内先息后本**。

- 先扣债权级未核销费用（`fee_amount` 减已核销费用）；
- 再逐期核销，每期先冲利息再冲本金；
- `OPEN`（未到期）期次不可核销，命中直接抛；
- **超额入金不自动分摊**：拆完还有余量（`remainder > 0`）直接拒绝（`RF_PAY_002`），走转工单 / 退款，
  不自动摊到后续期次——自动分摊会凭空产生「已到期」的核销事实，污染账务与征信报送口径。

**为什么先费用**：费用类不产生客户权益、也不随本金减少而减免，先收可避免欠费随时间扩大；
利息先于本金是避免「欠息滚入本金」把成本复利放大。这两条虽是行业惯例，但**必须落成代码断言**，不能靠口头约定。

**两层防护**：应用层拆完判 `remainder`；领域层 `Loan.applyAllocation` 再判一次「核销总额 > 余额」，
防止上层漏判。

**Q16：手续费和利息有什么区别？为什么不能合成一个字段？**

两个字段、两种来源、两种处理：

| | 手续费 `fee_amount` | 利息 `interest_accrued` |
|---|---|---|
| 来源 | 建债权时一次性给定 | 计息产生（计划生成时一次性计提） |
| 是否随本金递减 | 否 | 是（按期初余额计） |
| 核销顺序 | 最先 | 期内先于本金 |
| 提前结清时 | 未核销部分豁免 | 未到期部分豁免 |

合成一个字段会丢掉三件事：① 利息随余额递减而手续费不递减；② 减免额只作用于本金，
把费用塞进同一字段会让「减免额 ≤ 剩余本金」这条守卫失效；③ 余额不变式需要三个独立项才能精确对拍。

**余额不变式 INV-2**：`balance ≡ principal + fee + interest_accrued − Σ核销 − Σ豁免`，**精确相等、不容差**。
`ReconciliationApplicationService` 做三面对拍——存量面（`loans.balance`）、流水面（按上式推导）、
义务面（Σ期次未清偿 + 费用未清偿），三者必须一致。

**Q17：两级缓存怎么做的？为什么只缓存配置、不缓存账务数据？**

**落地形态**：L1 = Caffeine（进程内，默认 10s），L2 = Redis（跨实例，默认 60s），键前缀 `rf:`；
三级读取 L1 → L2 → 数据库 loader；空值哨兵防穿透；进程内单飞防击穿。

**失效策略**：配置写成功后**在事务提交后**删 L1 + L2，TTL 只做兜底。
为什么必须在提交后失效：事务提交前删，并发读会回源查到**旧值**又把它写回缓存，
形成「删了又写回」的竞态——这是缓存最常见的自伤方式。

**边界（白名单）**：Redis **只允许两类用途**——只读业务配置的 L2 缓存、网关限流状态。
**债权余额 / 核销流水 / 个人信息 / 征信结果 / 审查结果一律不进缓存**（`ADR-RF-012` §2、`AGENTS.md` B-13）。
理由不是「Redis 慢」，而是这四类数据的共同点是**会过期、会撤回、会变更，且带合规留痕要求**——
缓存一份旧余额进 Redis 等于制造第二份权威源；征信结果缓存一份等于扩大泄露面。

**降级**：Redis 不可用时自动**直读数据源**——缓存是优化，不是正确性来源。
正确性仍然只认 PostgreSQL（唯一索引 + `ON CONFLICT` + 乐观锁 `version`）。

**引入了 Redisson，但锁不是正确性来源**：共享 `common/lock` 提供分布式锁机制件（`ADR-RF-015`），
只覆盖「防重复进件 / 回调幂等」两条受保护写路径，用途是**收敛并发窗口**；
正确性仍然只认 PostgreSQL（唯一索引 + `ON CONFLICT` + 乐观锁 `version`）。
锁不可用一律 **fail-closed 拒绝写**（`RF_LOCK_002`/503），不降级放行——金融写路径宁可拒绝错，不可放行错。

**Q18：网关限流怎么做的？令牌桶为什么用 Redis 而不是本地计数？**

**落地形态**：网关 `RateLimitFilter`（order −90，早于路由）→ Redis 令牌桶（Lua 脚本原子扣减），
超限返回 **429 + `Retry-After`**，响应体沿用统一 `ApiResponse` 结构，错误码 `RF_GATEWAY_001`；
规则按路径 Ant **最具体优先**匹配（如 `/api/applications/**` 20/40、`/api/**` 500/1000 兜底），配额可配。

**追问：为什么留了两套限流实现？** 网关提供**双模式 + 一个开关**：
`retail.gateway.rate-limit.mode` = `redis`（**缺省**，Redis 令牌桶，多副本配额准确）／
`memory`（进程内令牌桶，零外部依赖，但**单实例口径**：多副本时放行量 ≈ 单副本额度 × 副本数）。
两套**互斥装配**——各自带互补的 `@ConditionalOnProperty`，同一时刻只注册一个限流过滤器，
**不会双重限流**（叠加会让额度减半且极难排查），并有专门的装配期单测钉死这条。
留两套而不删一套，是因为单实例部署或无 Redis 环境需要零依赖兜底，且切换**可回退**；
代价是两套都要维护、切错会静默降级成单实例口径，所以切模式必须显式登记。

**键怎么取**：网关本阶段**不验签**（鉴权下沉各服务本地验签），拿不到可信主体，
所以用 `Authorization` 头的 **SHA-256 哈希**区分调用方——**凭据本身不入 Redis 键**，无头时退化为来源 IP。
生产若网关改为验签，应改用主体 ID。

**为什么必须用 Redis 而不是本地计数**：多实例部署时本地计数会让实际放行量变成
「单实例额度 × 实例数」——限流直接失效。令牌桶的时间补充与扣减必须在 Lua 里**一次原子完成**，
否则并发下会出现超发。

**Redis 挂了怎么办**：**fail-open 放行**。限流是保护层，不是安全边界——
真正的重复提交已被服务内三层幂等（请求指纹 + 数据库唯一索引 + 业务唯一键）挡住。
取舍是明确的：Redis 故障期间超限请求会放行，生产可按风险切 fail-closed。

**Q19：为什么引入状态机引擎？领域状态机和框架引擎谁是事实源？**

**结论先行：领域状态图是唯一事实源，引擎只是执行器。**

- **领域侧**：状态与允许迁移写在聚合里（`LoanStatus` / `ReleaseOrderStatus` / `TitleRetentionStatus` 枚举 + 聚合根的迁移方法），
  `domain` 包**零 Spring 注解、纯 JUnit 可跑**——这是本仓红线，引擎**不得侵入**。
- **引擎侧**：Spring StateMachine 4.0.0 放在**独立模块** `statemachine`（`com.company.retail.statemachine`），
  只提供「按状态图执行一次迁移并返回结果」的底座；接线只放服务内 `*.application.statemachine` 包。
- **为什么值得引入**：手写状态机散落各服务，「这个状态允许去哪」得靠人读代码；
  引擎把状态图**显式化**，非法迁移在执行期就被拒绝，而不是等线上数据脏了才发现。
- **为什么不引外部中间件**：引擎是**进程内**的，不违反「不引 Seata / 分布式事务 / 对象存储」；
  版本锁 **4.0.0**（4.0.1+ 基于 Spring 6.2 会与本仓 Spring 6.1.15 BOM 打架，3.x 是 Spring 5.3 老线）。
- **面试加分点**：讲清「事实源 vs 执行器」的边界，比「我们用了 Spring StateMachine」值钱得多。

**Q20：外部回执重推，怎么保证不重复解押？**

**先讲清 bug 面**：DMZ 有三道关——nonce 防重放、scope 校验、IP 白名单。
但 **nonce 只挡「同一个 nonce 重放」**，挡不住外部方「换一个 nonce 重推同一业务回执」。
同一业务回执若入库两次，就会**重复推进解押状态、重复发闭环事件**——证据链出现两条同源回执。

**解法：以数据库唯一索引为权威，不引分布式锁。**

- 唯一索引 `uk_receipt_order_authority_ref (release_order_id, authority, COALESCE(receipt_ref, ''))`；
  回执号可空 → 用 `COALESCE` 表达式索引，让「无回执号的代录」同样受约束保护。
- 写入走 `ON CONFLICT DO NOTHING`（**不捕获唯一键异常**——PG 事务内一旦触发唯一键错误，整笔事务即被置为 aborted）；
  冲突返回 0 行即「已存在」→ 幂等返回，**不推进状态、不发事件**。
- 应用层两道闸只是**快路径**：① 写入前查既有回执；② 写返回 0 行 → 幂等返回。
  **并发窗口内两个线程可能同时通过「写入前查」，最终靠唯一索引收敛为一条——唯一索引才是权威。**

**为什么不用 Redisson 分布式锁**：锁不是正确性来源（唯一索引才是），引入它等于给受保护写路径
新增一个硬依赖与一个失败模式——**Redis 不可达就写不进去**，收益不足以抵消。
这条决策单独记了 ADR（回调幂等 `ADR-RF-013`、分布式锁 `ADR-RF-015`）。`ADR-RF-013` 原写「不引入分布式锁」，
2026-11-24 按用户指令修订：锁**一并引入**，但唯一索引仍是正确性来源、锁只收敛并发窗口。

## 6. 产品档位配置化 + 两级缓存 + 网关限流：已落地的实现与取舍

> **口径声明（面试前先看这条）**：本节描述的是**仓库已落地**的能力——V18 迁移新增产品档位目录与还款计划快照列，
> `common` 提供 Caffeine L1 + Redis L2 两级缓存机制件，网关提供**双模式令牌桶限流**（`redis` 缺省 / `memory` 进程内，一个开关互斥装配，`ADR-RF-012`）。**可以按「已有能力」讲**，
> 但必须带白名单边界：缓存只覆盖只读配置、限流只在网关侧、**不缓存账务数据与个人信息**。

### 6.1 落地前的问题：三层塌成了一层入参

`POST /api/repayment-plans` 的 `monthlyRateBp` 一个字段同时兼三个角色：
① **产品档位**（「36 期 0 息」这个产品本身是什么）；② **授信结论**（这笔单具体适用什么，可人工调额）；
③ **实际用值**（生成计划时到底用了多少）。

第 ③ 层**完全没落库**——`core.repayment_plans` 只有 `method / installment_count / first_due_date / bonus_month / plan_version`，
V1–V17 里零个利率列。**V18 已补上快照三件套**（`product_code` / `product_version` / `rate_bp`），这个问题现在是**已闭环**的。
落地前的后果很具体：**计划生成后无法复现当时的算法、无法重算对账**，
客户争议「当时到底几息」时数据库里查不出来，只能靠 `trace_id` 追日志。这是这个系统当下最实的一个欠账。

### 6.2 仓库里已经有两个现成范式（不用另起炉灶）

- **`core.decision_rules`（版本化配置表）**：`rule_version + scheme + config JSONB + effective_from + enabled + uk_rule_version`，
  注释明写「规则参数版本化（口径变更走配置）」，`R06` 补「规则版本化，不影响存量」。
  **但它在代码里零读写方、迁移里也没有种子数据——目前是空壳**，正好是「表建了不算功能有了」的反例。
- **`core.affordability_assessments`（已完整落地的快照范式）**：`policy_version + input_snapshot JSONB`，
  append-only，「只存输入与结果快照，不重算历史」，Mapper 有 insert + findLatest，是本仓最完整的样板。
- **`core.contracts.terms_snapshot`**（签约时点条款快照，append-only），由策略对象产出，是现成的「配置 → 快照」代码路径。

### 6.3 落地的三层结构（产品目录 / 授信结论 / 计划快照）

```
产品目录（配置表：版本化，读多写少）
   ↓ 选档
授信结论（决策：本次授信的实际条件 + 决定人 / 复核人留痕）
   ↓ 生成计划时合成，优先级显式定义
计划快照（落 repayment_plans：product_code / product_version / rate_bp）
   ↓
期次拆分结果（schedule_items，已有）
```

优先级**已写进代码并有单测**（纯领域 `ProductTermsResolver`，零 Spring 依赖）：
**授信覆盖值 > 产品默认值 > 两者都无则拒绝**，三者都进快照。
刻意收住的一个口子：手续费（`fee_amount`）**不进产品表**——产品表只定义「还款口径」（期数 / 月利率 / 奖金月 / 提前结清减免上限），
费用与费率属**合同条款**，进产品表等于绕过合同口径。所以「0 息产品手续费多少」仍人工传参，这不是遗漏，是边界。

### 6.4 为什么是「快照」不是「引用」（已落地）

配置会改、会下架；**改了配置不能改历史计划**。只存 `product_code` 引用，历史计划在配置变更后无法复现。
存快照（`product_code + product_version + rate_bp`）才能做到「配置变更不影响存量」——
这与支付能力评估的「不重算历史」是同一条原则，也是 `R06` 对 `decision_rules` 的原话：「规则版本化，不影响存量」。

### 6.5 配置与缓存的边界（最值得讲的一点，已落地）

- **配置版本化是正确性需求**（能不能复现、能不能审计），**缓存是性能优化**（读得快）。两者不能互相替代。
- 顺序上**先做版本化、再谈缓存**——本仓就是这个顺序：V18 先落产品目录与快照列，再上两级缓存。
- 缓存落的是**不可变快照**（带版本号 + 生效期）；失效靠**版本号 + 主动失效**（写成功**提交后**即清 L1 + L2），
  TTL 只做兜底；空值缓存 + 逻辑过期 + 互斥重建防击穿。
- **为什么在几十行的表上放两级缓存**：不是为了扛并发读，而是为了**承载变更失效的传播通道**——
  配置一改，所有实例必须立刻看到新值（`PUT` 改档位后缓存主动失效，E2E 有断言）。
  面试官第一问必然是「为什么需要」，答「为了性能」是减分项，答「为了失效传播 + 版本化读模型」才站得住。
- **降级**：Redis 不可用 → 直接直读数据源，**缓存不可用不影响正确性**。

**Redis 锁绝对不能当正确性来源**——这一条我们**落地**了，只是没有把它当正确性来源：
本仓幂等的最终权威仍是**数据库唯一索引 + `ON CONFLICT`**（含 V19 的回执唯一索引），
并发控制还压在乐观锁 `version` 与到期批量抢占锁。
已实现 Redisson 分布式锁（`ADR-RF-015`）只做两件事：把「同一客户同一台车并发进件」「外部方换 nonce 重推同一回执」
这两个**先查后插**窗口收敛掉；锁键按业务键摘要（不落明文），锁在**事务提交后**释放，
**Redis 不可达时 fail-closed 拒绝写**（503）而不是降级放行——宁可拒写不可重复写。
面试答法：锁是并发窗口的收敛手段，数据库才是正确性来源；两者职责不同，不是同一件事做两遍。

### 6.6 与既有配置体系的对照（体现「知道配置不是一坨」）

本仓已有两类配置，性质不同：

| | 系统参数级 | 业务数据级 |
|---|---|---|
| 例子 | `retail.contract.cooling-off-days: 8` | 产品档位（36 期 0 息） |
| 载体 | `application.yml` + 环境变量 | 数据库表 |
| 变更频率 | 低频（部署 / 环境级） | 低频但需留痕与审批 |
| 版本 | 无 | 必须有（版本号 + 生效期） |
| 追溯方式 | 靠部署版本 | 靠行版本 + 快照 |

`R01 §7` 登记了 16 个 `retail.*` 系统参数键。产品档位属于第二类——**业务数据，需要落库、需要版本、
需要审批留痕**，塞进 yml 会丢掉审计链。把这两类区分讲清楚，比堆技术名词有说服力。

## 7. 教育线架构师岗位迁移话术

面试主动引导："如果换成在线课堂业务，我会这样拆"——用同一套方法论映射：

| 本系统概念 | 课堂业务对应 |
|---|---|
| 双形态并行（分期/车贷） | 多业务线并行（直播课/录播课/1v1） |
| 冷静期 8 日 | 退费窗口期与退费状态机 |
| 合规门禁 fail-closed | 内容合规与未成年人保护闸门 |
| 三重放款门禁 | 开课前三重校验（师资/课包/合同） |
| 贷后对拍 / 日批对账 | 订单结算与分账对账日批 |
| 双主体 JWT（员工/客户） | 员工/学员/家长多主体认证 |
| 外部机构模拟器联调 | 支付/短信/推流等外部依赖的模拟验收 |

卖点是**从 0 到 1 的架构方法论**（领域建模 → ADR → 并行分包 → 验收判据），
而非金融域知识本身。
