## 1. 项目一句话定位

> **形态口径提醒**：本项目主形态是**个品分期（个别信用购买斡旋，《分期付款销售法》体系）**，
> 钱由信贩**代付给销售店**、消费者向信贩分期支付，担保是**所有权保留**（不是抵押、不是无担保信用贷），
> 额度基准为**个别支付能力预估额**；系统按**双形态并行**（个品分期 + 汽车贷款）建模。
> 简历与面试中一律不要简写成"信用贷"。

覆盖进件 → 征信 → 授信 → 合同 → 放款 → 账务 → 贷后 → 解押的**全信贷生命周期**，
Spring Cloud 微服务架构，12 个部署单元，按持牌消费金融合规要求设计（同意门禁 / 三重放款门禁 /
总量规制预估额 / 报送与对拍闭环）。

## 4. 架构叙述主线（按此顺序讲，5 分钟讲完）

1. **领域建模先行**：先做 12 个限界上下文的领域发现与上下文映射（`R02 §5`），再定服务边界——
   服务拆分是领域建模的结果，不是起点。
2. **拆分判断原则**：担保物形态不同必拆（车辆抵押 vs 商品所有权保留），通道能力相似必合
   （征信报送、银行代付、送达都是通道层）。不谈"生命周期长短"这类模糊标准。
3. **中台复用画界**：复用"能力"（契约 jar、错误码、事件常量、征信通道适配器），
   不复用"数据和状态"——否则中台退化为分布式单体。落法 = 契约冻结（`w2-frozen`）+ 事件白名单。
4. **双形态并行**：业务裁决"双形态并行"（`ADR-RF-002` Accepted），用 4 个策略点承接形态差异，
   而不是等业务定死后硬编码；形态反转的逐项返工量已预先评估（`R11 §8`）——架构允许低成本返工。
5. **数据隔离渐进**：第一版共库不同 schema + 明确的演进触发器（冲突写入集 / QPS 阈值），
   不一步到位拆库；独立库实例、独立号段、独立密钥（三把 JWT secret 互不相同）先隔离。
6. **验收判据先行**：契约冻结后才能开并行窗口；每个工作包以"合后全量构建 + 走网关冒烟 + E2E"
   为放行判据，文档一致性由 15 项机器校验守门。

## 5. 高频追问 Q&A（每条都有真实实现兜底）

**Q1：Outbox 为什么不直接发消息？**
本地事务写业务表与写 outbox 表在同一事务内，保证"状态变更"与"事件产生"原子；后台调度投递，
失败落 `outbound_tasks` 人工补发兜底。17 类事件走白名单校验（EventPayloadGuard），防止
payload 字段漂移。直接发消息无法保证两者原子性，这是选型的根本原因。

**Q2：合规门禁为什么 fail-closed？**
金融场景里"放行错"的代价（无同意报送征信 = 合规事故）远大于"拒绝错"（可重试）。
门禁取不到同意证据时一律拒绝。真实教训：事件驱动报送在调度线程执行，无请求上下文，
透传认证 401 → 报文永远 DEAD；修复 = 机器场景签发 `svc-*` 服务 token（`ConsentGateFacade`），
用户场景仍零信任透传。这个缺陷是模拟器联调暴露的——单测 mock 了门禁，e2e 未覆盖该断言，
说明"集成盲区要靠真实对端暴露"。

**Q3：nonce 防重放怎么保证原子性？**
nonce 以数据库唯一约束原子写入（重复回放写不进 → 409），不做"先查后插"（有竞态窗口）。
完整三关：HMAC-SHA256 规范化串验签（401）→ nonce 防重放（409）→ scope + IP 白名单（403），
全部留痕 `call_logs`（append-only，只追加不修改）。

**Q4：为什么自研模拟器？**
外部机构调研签约是长周期日历依赖，不能阻塞开发。零依赖 Node 模拟器实现六向对端
（征信/银行代付/eKYC/DMS/送达/入金文件），把"等外部"变成"对模拟器验收"。回报是抓出
4 个真缺陷：PartnerRegistry 密钥硬编码只认测试机构、保留登记与兜底建单的并发竞态 409、
构造器歧义导致服务启动失败、GET 请求携带 null body 违反浏览器 fetch 规范（只有真实浏览器触发）。
外部机构真实接入时只换 URL，报文差异由双模适配器消化。

**Q5：数据库为什么不一步到位拆库？**
共库不同 schema 起步：事务边界内简单、跨域查询明确、迁移成本低；同时预登记演进触发器
（写入集冲突 / QPS 阈值），到点按域拆库。直接每域独立库，跨域一致性（对拍、核销）成本翻倍，
早期是纯负担。隔离性先用"独立实例 5435 + 独立号段 + 独立密钥"保障。

**Q6：万一业务形态反转（分期改车贷为主）怎么办？**
`R11 §8` 有逐项返工量评估：双形态并行 + 4 个策略点（形态差异收敛在 4 个注入点），
反转只动策略点配置与对应域服务，不动共享底座。核心观点：**业务线会反转，架构要允许低成本返工，
所以每个重大决策都写 ADR 留痕**。

**Q7：服务间调用怎么保证安全与合规？**
员工/客户双主体 JWT（两把独立密钥，伪造 token 401）；服务间走 Feign 契约门禁（代付前三门禁：
合同 / 同意 / 审查，任一不过 fail-closed）；DMZ 只暴露外部回调入口，过三关后由系统服务 token
转发内部，外部调用方永远拿不到内部凭据。

**Q8：持久层为什么用 MyBatis 注解 SQL，不用 JPA、也不用 XML？**
①**不用 JPA**：金融账务要的是**锁语义与 SQL 的完全可控**（`SELECT ... FOR UPDATE` 行锁、`ON CONFLICT` 幂等、
精确相等的不容差对拍），JPA 的自动 flush 会让"同一事务内先写后读"的判断变得不可预期。
②**不用 XML、只用注解 SQL**：SQL 就写在 Mapper 方法上，一眼看清这条接口到底打了几条 SQL、锁在哪张表，
不用在 XML 与接口之间来回跳；Mapper 接口本身就是持久层的**端口契约**，业务层不感知持久化实现。
③**行映射显式化**：查询结果统一映射成 `Map<String,Object>`，再由共享的 `RowValues` 按列名取值——
`getLong` 遇 NULL 返 0、`getString` 遇 NULL 返 null 这类口径在映射层就锁死，不依赖 ORM 的隐式类型推断，
也不让枚举 / 字符串转换散落在几十个 RowMapper 里。
④**装配纪律**：每个服务 `@MapperScan` 显式列出**自己的** mapper 包，不做全包扫描；
共享 infrastructure 的 mapper 由共享配置类单独注册。
⑤迁移用 Flyway 版本化，**已执行迁移字节不可改**，任何结构调整都走新迁移，schema 与代码的差异可审计。

**可以主动讲的迁移经历**：本项目最初是手写 `JdbcTemplate` + `RowMapper`，后来统一迁到 MyBatis 注解 SQL。
迁移红线是**SQL 语义、方法签名、事务边界、对外接口一律不变**——具体做法：Mapper 一律返回 `Map` 结果 +
`RowValues` 显式取值（保住原 RowMapper 的 NULL 口径）；唯一键幂等统一走 `ON CONFLICT` 原子语义
（`ON CONFLICT DO NOTHING`，而不是"捕获唯一键异常再重读"——PostgreSQL 事务内一旦触发唯一键错误，
整笔事务即被置为 aborted，无法继续读库）；一级缓存显式降级为 STATEMENT 级，
对齐原来"每次读都落库"的读语义，避免同一事务内重复 SELECT 命中本地缓存旧行。

**Q9：为什么不引完整的 Spring Security？**
只要 `spring-security-crypto`（BCrypt 口令散列），过滤链自研：这套系统要**双主体**（员工 / 客户两把密钥）
与**零信任服务间调用**，标准过滤器链表达不了"主体类型在验签层强制"和"外部方只经 DMZ 入口"这两条，
自研拦截器反而更短、更可控。

**Q10：Spring 的 BOM 顺序为什么手动前置？**
父 pom 把 `spring-framework-bom`（6.1.15）声明在 `boot-dependencies` 之前——Maven BOM 取**先声明者**，
Boot 3.2.5 自带的 Spring Framework 6.1.6 没有 `HttpHeaders.headerSet()`，而 Gateway 4.1.6 需要它。
这类"版本解析顺序"坑不写进文档，下次升级 BOM 就会以编译失败的形式暴露。

**Q11：为什么不用 MQ？**（决策依据 `ADR-RF-008`，`AGENTS.md` B-10 列为业务红线）

五层理由，从"最该讲"到"背景"：

1. **需求不匹配（本质）**：全系统的跨服务同步只有**一类**要求强一致——放款前的"合同 / 同意 / 审查"三重门禁，
   那必须走同步 fail-closed 调用。其余全是**事后状态同步**（结清 → 建解除单、逾期 → 触发报送），
   容忍秒级最终一致。MQ 解决的是高吞吐、大扇出、跨团队解耦，这里一条都用不上——**引 MQ 只是把轮询换成订阅，业务语义一点没变**。
2. **MQ 解决不了真问题**：用 MQ 仍然要解决"业务写 + 发消息"的原子性，最后还是得配 outbox 或事务消息。
   MQ 只解决"消息传输"，没解决"状态与消息的原子性"，等于**多一套可靠性语义**（重复 / 顺序 / 积压 / 重平衡 / 死信 / 消费幂等），
   而这些在 outbox 侧已经用表约束表达清楚了（`event_consumptions` 主键 = 消费幂等，`outbound_tasks` = 人工补发）。
3. **公司既定口径**：同公司另一条业务线的定源 ADR 明确写"不引入外部组件：不引 MinIO/S3/对象存储、不引 MQ/Seata"，
   本项目选择与之对齐的微服务形态（`ADR-RF-001`），所以是**不允许**，不是没想到。
4. **金融账务的风险偏好**：全局锁 + 回滚日志在金融账务上风险过高（`R02 §7`）。
   outbox 的每一步都落在表里，**可验证、可排障、可重放**；消息进了 broker 就不可见，在审计场景反而是减分项。
5. **合规面最小**：本项目有大量含个人信息的附件与报文，每多一个外部组件就多一份委托方 / 数据驻留 / 审计边界的评估面——
   "少一个外部系统"本身就是安全收益（`ADR-RF-008` 背景）。

**代价（要主动说，显得诚实）**：秒级延迟（轮询 1s）、DB 承担投递负载、水平扩展前必须把消费游标改成 `FOR UPDATE SKIP LOCKED`
（`RfEventDispatcher` 类注释已注明当前单实例成立）、排障靠查表而非 broker 面板。

**什么情况下会引入 MQ（演进触发器）**：日均事件量到百万级、单表轮询顶不住、需要跨机房或多集群扇出。
到点再评审，不需要提前为假想的规模付运维成本。

## 6. 教育线架构师岗位迁移话术

面试主动引导："如果换成在线课堂业务，我会这样拆"——用同一套方法论映射：

| 本系统概念 | 课堂业务对应 |
|---|---|
| 双形态并行（分期/车贷） | 多业务线并行（直播课/录播课/1v1） |
| 冷静期 8 日 | 退费窗口期与退费状态机 |
| 合规门禁 fail-closed | 内容合规与未成年人保护闸门 |
| 三重放款门禁 | 开课前三重校验（师资/课包/合同） |
| 贷后对拍 / 日批对账 | 订单结算与分账对账日批 |
| 双主体 JWT（员工/客户） | 员工/学员/家长多主体认证 |
| 外部机构模拟器联调 | 支付/短信/推流等外部依赖的模拟验收 |

卖点是**从 0 到 1 的架构方法论**（领域建模 → ADR → 并行分包 → 验收判据），
而非金融域知识本身。
