# 面试专题 · 并发与一致性话术核查（通用话术 vs 本项目真实架构）

> **文档定位**：记录对一段外部通用「车贷系统高并发面试话术」的逐条核查。
> 该话术概念层面（脉冲洪峰 / 资金安全 / 削峰填谷）方向正确，但**技术选型落到了另一套栈上**——
> Kafka、Redisson 在本仓库**仍无实现**；
> **RocketMQ 已于 2026-11-23 引入**（`ADR-RF-014`：MQ 削峰 + 密文信封投递），但**默认关闭**——
> 讲的时候必须说清「默认走同步路径，开了才走 MQ」；
> **Spring StateMachine 引擎已落地**（独立 `statemachine` 模块，领域状态图仍是唯一事实源）；
> Redis / Caffeine 与网关限流**已落地，但用途被白名单锁死**（只读业务配置缓存 + 网关限流状态，`ADR-RF-012`），
> 讲法必须按「白名单边界」讲，不能吹成「缓存账务热数据 + 全局限流平台」。
> 本文件把「哪些能讲、哪些不能讲、正确版怎么讲」钉死，避免面试时被追问击穿。
>
> **归属**：个人求职材料，不纳入 `docs/` 登记，`check_docs.py` 不扫描 `interview/`，文件计数护栏不受影响。
> **事实源**：数字与口径以 `PROGRESS.md`（唯一事实源）与 `interview/简历-项目经历.md` §6 速查表为准。
> **系统未上线、无生产流量**：不得补写 QPS / 用户量 / 交易笔数 / 「支撑大促洪峰」等线上规模指标。

## 1. 核查结论（先看这条）

**那段话术不能照着讲。** 它描述的是「典型金融高并发系统」的通用模板，不是这个仓库真实落地的系统。
面试官只要顺着任何一项技术追问实现细节（集群规模、命中率、锁的红锁处理、状态机框架配置），
都会出现「简历上有、代码里没有」的当场穿帮。

这不是措辞问题，是**事实层冲突**：项目在 `AGENTS.md` B-10 把「不引 MQ」列为业务红线，
MQ / Seata / 对象存储**至今未引入**。Redis 是**后开的窄口子**：W-MB 那轮确实没引，
W-CACHE 轮按用户授权引入，但用途被 `ADR-RF-012` §2 与 `AGENTS.md` B-13 锁死为两类
（只读业务配置的 L2 缓存 + 网关限流状态）——**不缓存余额 / 核销流水 / 个人信息 / 征信与审查结果**。
反过来把 MQ 写进话术，等于把自己团队最硬的架构决策讲反了；
把 Redis 吹成「缓存账务热数据」，等于把白名单边界讲穿。

## 3. 本项目真正能讲出深度的三个看点

卖点不放「扛 QPS」，放**高并发下不出资损 / 不双花 / 状态不错乱**。

### 3.1 资金一致性 —— `retail-core`（刻意不拆）

- 入金核销 + 余额 + 债权终态落在**同一本地事务**，拆开必然引入分布式事务或补偿。
- 入金核销严格按「费用 → 利息 → 本金」拆分，期次内先息后本；超额入金转人工工单，不自动分摊。
- 余额对拍**精确相等、不容差**：余额 ≡ 代付本金 + 手续费 + 利息 − 已核销本金。
  容差会让每天 1 日元的系统性偏差长期潜伏，几年后变成资损。
- 到期批量用**单条 SQL 抢占锁**（唯一约束 + 冲突更新 + 条件更新）：不重复执行、失败可重试、僵尸 RUNNING 可接管。

### 3.2 fail-closed 门禁 —— 放款前三重同步门禁

放款前依次问合同 / 同意 / 审查三方，任一**超时、拒绝、状态未知**一律拒付并整体回滚。
同意取不到证据同样拒绝而非放行。金融场景「放行错」的代价远大于「拒绝错」。

### 3.3 状态机 + Outbox —— 跨服务一致性与语义建模

- 状态变更只能走聚合根状态机方法，只允许迁移到允许的后继状态，**终态不可再迁移**；
  `underwriting-service` 在聚合层硬阻断职责分离、征信未完成不得决定、决定必须锚定有效同意。
- `title-release-service` 8 态解除状态机强制「文件出具」与「登记完成」两态分离，外部回执为唯一权威。
- 事后同步走 Outbox：状态变更与事件产生同事务，at-least-once 投递，消费侧幂等，失败进 DEAD 不阻塞链路。
- 17 类事件常量 + 事件载荷白名单守卫（默认拒绝），从发布端杜绝个人信息进入事件载荷。

## 4. 修正版模拟问答（可直接背诵）

**Q：放款高峰第三方回调瞬时洪峰，怎么削峰？**
> 分两层说：**一致性**和**削峰**不是一回事。
> 一致性靠 Transactional Outbox——状态变更与事件产生放在同一本地事务，保证原子性，
> 后台轮询投递，at-least-once，消费侧幂等，失败落 DEAD 人工补发，**不引入分布式事务**。
> 削峰是 2026-11-23 之后补的一层：引入 RocketMQ 作为 outbox 之上的**缓冲层**，
> 外部机构调用（征信报送）、大文件落盘、法定文件送达这些慢动作，
> 由「控制器封**密文信封**丢进 MQ、消费者解密后执行同一 handler」承接——
> **MQ 上只允许出现密文**，明文个人信息一律不入队，因为 broker 的落盘行撤不回来。
> 这个开关默认是关的：开着是异步路径，关着走同步路径，行为完全一致。
> 边界说清楚：**outbox 仍是唯一真相源，MQ 不参与事务**，它解决的是洪峰，不是一致性。

**Q：网络重推怎么保证不重复放款？**
> 三层幂等，各堵一个漏洞：请求指纹挡「同键不同内容」的误重放；数据库唯一索引兜底并发插入；
> 业务唯一键兜底「换了幂等键也挡不住重复代付」。数据库层用 `ON CONFLICT` 做原子语义，
> 不采用「先查后插」——PostgreSQL 事务内一旦触发唯一键错误，整笔事务即被置为 aborted，无法继续读库。

**Q：多线程并发改订单状态怎么保证不错乱？**
> 不提供任何直接改状态的入口，状态迁移只能走聚合根的状态机方法，只允许迁移到当前状态允许的后继状态，
> 终态不可再迁移。审查服务还在聚合层硬阻断职责分离和「征信未完成不得决定」两条不变式。
> 状态机是纯 Java 写的，domain 层零 Spring 依赖，可以用纯 JUnit 跑，不依赖任何状态机框架。

**Q：为什么没做多级缓存？热点配置怎么扛？**
> 先纠正一点：**多级缓存已经做了**，但只用在「读多写少、且改了不影响历史事实」的地方——
> 产品档位这类**配置数据**，走 Caffeine L1（进程内）+ Redis L2（跨实例）两级。
> 刻意**不做**的是给账务数据加缓存：余额、核销流水加缓存，「读到旧余额」比「多查一次库」危险得多，
> 所以 MyBatis 一级缓存显式降为 STATEMENT 级，对齐原来「每次读都落库」的语义。
> 缓存边界写死在 `ADR-RF-012`：**Redis 只允许两类用途——只读配置缓存 + 网关限流状态**；
> 征信结果、审查结果、个人信息一律不进缓存（征信结果属合规敏感数据，缓存了等于扩大泄露面）。
> 失效策略是「**事务提交后主动删两级 + TTL 兜底**」：在事务提交前删，会出现并发请求回源读到旧值、又把旧值写回缓存的竞态。
> Redis 挂了直接降级直读数据库——**缓存是优化不是权威源**，正确性永远只认 PostgreSQL。
> 另外产品档位改版采用「旧版本封口停用 + 新版本插入」，不原地覆盖；
> 还款计划侧落**快照**（档位码 / 版本 / 利率基点），所以**改配置不会改历史计划**。

## 5. 使用红线

1. **只讲仓库里有的技术**：Kafka / Redisson 一律不讲；
   **RocketMQ 要讲，但必须带上三条边界**——默认关闭、只当缓冲层不做真相源、MQ 上只有密文信封（`ADR-RF-014`）；
   **Spring StateMachine 引擎已落地**，讲法是「领域状态图是唯一事实源，引擎只做执行器」；
   **Redis / Caffeine / 网关限流可以讲，但必须按 `ADR-RF-012` 的白名单讲**——
   缓存只覆盖只读配置、限流只在网关侧且 Redis 不可用时 fail-open；
   **不得夸大成「缓存账务热数据」「全局流量治理平台」**，也不得报任何 QPS / 命中率数字（本地单实例、无生产流量）。
2. **系统未上线**：不声称生产流量、大促洪峰、QPS、用户量、交易量；问「上线了吗」如实说没有。
3. **只讲自己负责的 4 个服务 + 契约底座**（retail-core / underwriting / bureau / title-release），
   其余 6 个业务服务与前端明确说是团队成果。虚构全包揽最容易被追问击穿。
4. **形态口径**：主形态是个品分期（信贩代付销售店 + 所有权保留），不是无担保信用贷；
   「日本」仅指业务法规域，被问落地细节按「设计 + 全链路仿真验证」陈述。
5. 被深挖时用 `PROGRESS.md §6` 验证记录、`docs/adr/` 决策留痕与 `interview/简历-项目经历.md` §6 数字速查表兜底。
6. 面试前跑一次 `python scripts/check_docs.py`（应 PASS / EXIT 0）——文档即证据链。
