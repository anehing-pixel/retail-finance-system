# 项目经历 · 能力叙事与追问库（不是微服务清单版）

> **用途**：把本项目写成“我在团队里真实负责的那一部分”，而不是“12 个微服务全是我做的”。
> 本文提供：可独立认领的**主责包菜单**、每个功能的**问题 → 排查 → 解决**模板、面试追问 Q&A、三套简历 bullet。
>
> **事实源**：代码与 `PROGRESS.md`；数字以当前仓库为准（18 个 Maven 模块、12 个长驻部署单元 + `db-migration` 作业、Flyway V1–V22、661 单测）。
> **重要边界**：系统**未上线、无生产流量、无真实客户**；外部机构只完成协议与模拟器验证，未真实签约联调。
> 不得补写 QPS、用户量、交易笔数、生产故障时长等线上指标。
>
> **使用方式**（建议按顺序）：
> 1. 在 §3 的主责包里，只勾选你**真实做过、且能连续讲 30 分钟**的 2–3 个；
> 2. 从 §4 选 3 个能讲透的案例（至少一个“踩坑/排查”故事）；
> 3. 用 §8 对应方向的 bullet 替换 `[ ]` 占位符；
> 4. 用 §6 自测，答不上来的包从简历里删掉。
>
> **本文不替你判断你真实负责了什么**。它给的是“可认领的叙事单元”和“边界句”，你按实际挑选。

## 0. 先解决“你到底负责什么”

### 0.1 三种可信的角色口径（按实际选一个）

| 口径 | 适用情况 | 开场句 |
|---|---|---|
| **技术负责人 / 核心后端** | 你确实参与架构、契约、评审与合并 | “我在 [N] 人团队里负责核心账务与跨服务一致性这条线，同时参与契约冻结和上线门禁。” |
| **核心后端（模块 owner）** | 你负责 1–2 个模块，不负责整体架构 | “团队负责整体架构，我负责账务/一致性这条线；其他模块由同事实现，我们通过契约和事件协作。” |
| **平台/基础设施后端** | 你主要做出站、异步、DB、CI 等横向能力 | “我不按业务服务划分，主要负责跨服务的可靠性底座：outbox、外部调用治理、数据库与发布门禁。” |

> **不要**用“12 个服务全是我一个人做的”。真实团队里这句话会被追问穿；
> 也不要用“我参与了所有设计”这种无法验证的表述。

### 0.2 面试官问“这都是你做的吗”时的标准答法

> “不是。这个项目是团队交付，我负责的是 **[主责包 A/B/C]** 这条线；
> **[其他模块/前端/真实外部联调]** 是同事或下一阶段的工作。
> 我简历里只写我实际负责的部分。对不是我写的东西，我能讲清接口、契约和验收边界，但不会把团队成果算成个人成果。”

这句话要背熟。它同时解决三个质疑：**真实性、边界感、团队协作**。

### 0.3 三个“边界句”模板

- **模块边界**：“我负责账务与一致性；客户、合同、前端由同事负责，我们通过 Feign 契约和 outbox 事件协作。”
- **阶段边界**：“系统完成了全链路仿真和真实浏览器验收，但未接生产流量；真实机构联调是下一阶段。”
- **决策边界**：“架构方案是团队评审的；我负责的是其中 [账务/一致性/安全] 的落地与验证，能讲清取舍和被拒方案。”

## 1. 为什么放弃“微服务清单”叙事

微服务清单回答的是“系统长什么样”，面试官真正想验证的是：

1. **你个人解决了什么问题**（不是团队有什么）；
2. **问题为什么难**（约束、失败模式、取舍）；
3. **你怎么定位和验证**（证据，不是感觉）；
4. **你的边界在哪**（哪些不是你做的，团队怎么协作）。

微服务清单的三个问题：

- **信息密度低**：列 10 个服务名，不等于你有 10 份深度；
- **诱导全包质疑**：“12 个服务都是你做的？”——一旦解释不清，整段经历可信度下降；
- **把你拉到架构名词竞争**：面试官总能问得更深，而你的真实贡献可能只在其中两条链路。

**更好的主线**：

```
业务结果 → 我负责的问题域 → 关键约束/失败模式 → 我的取舍 → 怎么验证 → 边界
```

服务名只作为“范围锚点”出现，不作为叙事脊柱。

## 4. 功能 → 问题 → 排查 → 解决（深挖案例）

> **面试官的追问通常有三层**：
> 1. **为什么**：为什么这样设计？约束是什么？被拒方案是什么？
> 2. **怎么做**：机制落在哪？失败模式怎么处理？
> 3. **怎么证明 / 失败怎么办**：有什么证据？如果重来怎么改？
>
> 下面的案例都按这三层准备。先选 3 个，按“现象 → 排查 → 解决 → 验证 → 追问 → 边界”讲。

### 案例 1｜代付只发生一次：三层幂等 + 数据库唯一索引

- **场景/目标**：同一合同在网络重试、并发请求、进程崩溃重试下，只能产生一笔代付。
- **我的边界**：核心账务侧；银行内部去重不假设。
- **现象/难点**：
  - 只在网关加 `Idempotency-Key` 不够：同一个键可能对应不同请求体；不同键也可能对应同一合同。
  - “先查再插”有竞态窗口；两个请求可能同时查到“未代付”。
- **排查**：
  1. 画调用链：网关幂等 → 账务落库 → 银行适配器 → 回调。
  2. 分别构造三种重复：同键同内容、同键不同内容、不同键同合同。
  3. 在真实 PG 上并发压测，观察唯一键冲突与事务状态。
- **解决/取舍**：
  - **请求指纹**：防“同键不同内容”的误重放。
  - **数据库唯一索引**：并发插入只能成功一条。
  - **业务唯一键**：即使换了幂等键，同一合同也不能二次代付。
  - 唯一键冲突用 `ON CONFLICT DO NOTHING` / `RETURNING`，**不捕获唯一键异常再重读**——PostgreSQL 事务内一旦唯一键错误，整笔事务会被置为 aborted，后续读也失败。
  - 资金动作**代码级禁止自动重试**，只允许人工/状态机补偿。
- **验证**：并发测试、真实 PG 唯一约束、走网关冒烟；库内代付行/事件各 1 条。
- **追问**：
  - Q：为什么捕获唯一键异常不行？→ PG 事务 aborted，必须用 `ON CONFLICT` 原子语义。
  - Q：三层是不是过度设计？→ 三层各堵不同漏洞：同键不同内容、并发插入、换键同合同。
- **诚实边界**：不假设银行侧一定去重；银行内部清算不在我范围内。

### 案例 2｜Outbox 不丢不重：本地事务 + 多实例原子认领

- **场景/目标**：业务状态变更与事件产生必须同生共死；多实例消费不能重复执行。
- **我的边界**：outbox 机制件；各服务的消费者由对应模块负责。
- **现象/难点**：
  - 直接“写库 + 发消息”是双写：进程崩溃可能库成功、消息失败。
  - 多实例同名 consumer 会互相覆盖游标，同一事件被执行多次。
- **排查**：
  1. 在事务边界上标注“写业务表”和“发消息”两个动作，确认无法原子。
  2. 起两个实例消费同一事件，观察 `event_consumptions` 与游标。
  3. 模拟消费失败/进程退出，检查租约与重试。
- **解决/取舍**：
  - outbox 表与业务表**同一本地事务**写入；后台轮询投递，at-least-once。
  - `(event_id, consumer)` 唯一键；`PENDING/FAILED → PROCESSING` 原子认领 + 5 分钟租约，只有一个实例执行。
  - 状态写只允许认领者（`status='PROCESSING'`）更新；游标 `GREATEST` 只前进，不回退。
  - 失败 3 次置 `DEAD`，不阻塞整条链路；MQ 只作可选削峰，不取代 outbox。
- **验证**：14 例单测；真实 PG 实测首次认领 1 行、租约内二次认领 0 行、过期可重认领、条件写 0 行、游标只前进；冒烟 52 条消费全 DONE、0 条卡死。
- **追问**：
  - Q：为什么不用 MQ 直接做一致性？→ 无法保证“库写成功”和“消息发出”原子；MQ 不能做真相源。
  - Q：at-least-once 怎么保证不重复？→ 业务唯一键 + 消费幂等，不追求 exactly-once。
- **诚实边界**：MQ 默认关闭；未维护生产 MQ 集群。

### 案例 3｜外部回执换 nonce 重推：表达式唯一索引 + 两态分离

- **场景/目标**：合作方重推同一业务回执（甚至换 nonce），不能产生第二条回执、不能重复推进解押。
- **我的边界**：title-release 回调与状态机。
- **现象/难点**：
  - nonce 只能防“同一报文重放”；对方换 nonce 重推同一业务回执时，DMZ 会放行。
  - “先查后插”在并发下仍可能插两条。
- **排查**：
  1. 用相同 `releaseOrderId + authority + receiptRef`、不同 nonce 连续重推。
  2. 观察回执行数、事件数、状态迁移次数。
  3. 检查是否存在业务唯一索引；确认 `receipt_ref` 可为空，普通唯一索引不适用。
- **解决/取舍**：
  - 表达式唯一索引：`(release_order_id, authority, COALESCE(receipt_ref,''))`。
  - 写入走 `ON CONFLICT DO NOTHING`；只有真正插入成功才发闭环事件。
  - 分布式锁只收敛并发窗口，**唯一索引才是正确性来源**；锁不可用 fail-closed 503。
  - 状态机强制“文件出具”与“登记完成”两态分离，合作方自证不算完成。
- **验证**：并发重推 + 换 nonce 重推，回执行 1、事件 1、状态只推进一次；E2E 负例（合作方自证）被拒。
- **追问**：
  - Q：有锁了还要唯一索引？→ 锁只减少冲突，不能跨故障/过期保证唯一。
  - Q：为什么用表达式索引？→ `receipt_ref` 可空，普通唯一索引对 NULL 不去重。
- **诚实边界**：未对接真实登记机关，回执权威性按协议建模。

### 案例 4｜Redis 宕机锁路径 500→503：异常链与 fail-closed

- **场景/目标**：受保护写路径（防重复进件/回调幂等）在 Redis 不可用时必须明确拒绝，而不是 500 或放行。
- **我的边界**：分布式锁机制件。
- **现象/难点**：
  - Redis 宕机时接口返回 500 `SYS_001`，不是预期的 503 `RF_LOCK_002`。
  - Redisson 抛的是包装异常 `RedisException("Unexpected exception while processing command")`，不是 `RedisConnectionException`。
- **排查**：
  1. 停 Redis，复现接口；抓异常栈和异常链。
  2. 对照捕获分支，发现只识别了 `RedisConnectionException`。
  3. 检查释放路径：释放失败是否把已成功的写翻成 500。
- **解决/取舍**：
  - 按异常链判定 Redis 类故障；统一映射 503 `RF_LOCK_002`，**fail-closed 拒写**。
  - 锁在事务提交后释放（`afterCompletion`）；释放失败只告警，不改变已成功的业务结果。
  - 锁键用用途 + 摘要，不落明文业务标识；不同写路径分锁，避免持锁调下游自死锁。
- **验证**：包装异常单测、Redis 停机冒烟；锁不可用时库内无写入，恢复后可写。
- **追问**：
  - Q：为什么不做 fail-open？→ 受保护写路径放行会产生重复进件/重复回执，宁可拒绝。
  - Q：锁是正确性来源吗？→ 不是；DB 唯一索引/乐观锁才是，锁只缩小窗口。
- **诚实边界**：锁只用于两条写路径，不承担全部并发控制。

### 案例 5｜限流 Redis 故障：fail-open 改 fail-closed + Sentinel + 告警

- **场景/目标**：Redis 不可用时，生产不能静默绕过限流；同时要有高可用与可告警。
- **我的边界**：网关限流与 Redis 部署模板。
- **现象/难点**：
  - 原默认 `fail-open=true`，Redis 故障时请求全部放行，限流形同虚设。
  - 只有本地单实例 Redis，无生产拓扑；双实现若同时装配会双重限流。
- **排查**：
  1. 查配置默认值与过滤器异常分支。
  2. 验证两套限流实现的条件装配是否互补。
  3. 检查 Redis 故障时是否有 ERROR 日志/告警标记。
- **解决/取舍**：
  - 默认改 `fail-open=false`：Redis 不可用返回 503；仅本地 dev 显式 fail-open。
  - 两套实现用互补 `@ConditionalOnProperty` 互斥装配，装配测试钉死“只能有一个过滤器”。
  - 新增 Sentinel 高可用模板（1 主 2 从 3 哨兵，quorum=2）与故障转移演练。
  - Redis 不可用输出 `ALERT_RATE_LIMIT_REDIS_UNAVAILABLE`（`failMode=CLOSED|OPEN`），实例级 10s 节流，避免日志洪泛。
- **验证**：默认 fail-closed 单测；告警标记单测；Sentinel 演练 `FAILOVER_OK`（主节点从 172.25.0.2 切到 172.25.0.3）；限流冒烟 redis 29/29、memory 33/33。
- **追问**：
  - Q：为什么生产不 fail-open？→ 可用性 vs 保护；生产 503 是显式失败，静默放行会让限流失效。
  - Q：为什么还保留 memory 模式？→ 单实例/无 Redis 场景的零依赖回退；多副本必须 redis 模式。
- **诚实边界**：Sentinel 是部署模板，生产网络/TLS/口令托管仍是运维落地。

### 案例 6｜运行期 DB 超管 → 受限角色：权限矩阵与补偿授权

- **场景/目标**：11 个连库单元不再用 `postgres` 超管，运行期角色隔离真正生效。
- **我的边界**：数据源配置、启动门禁、迁移账号、V22 授权。
- **现象/难点**：
  - 所有服务默认 `postgres`，角色授权只是“配置正确”，运行期不生效。
  - 切受限角色后，跨 schema 的真实访问会缺权限：bureau 要读 integration、underwriting 要读写 outbound_tasks、customer 要用 core outbox。
- **排查**：
  1. `grep` 所有 datasource 配置，确认 11 个连库单元。
  2. 按模块列出真实 SQL 访问的 schema/表，找共享机制件（outbox/inbox）的跨域需求。
  3. 用 `pg_stat_activity` 确认运行连接用户；用角色直连测试 `CREATE TABLE`、`pii.customer_pii`、`integration.partners`。
- **解决/取舍**：
  - 业务 9 服务 → `retail_app_rw`；customer → `retail_pii_rw`；external-api → `retail_dmz_rw`。
  - 新增启动门禁 `RfDataSourceGuardConfig`：超管/未知角色/弱口令直接启动失败。
  - Flyway 用独立迁移账号；运行池不持有 DDL。
  - V22 按真实访问路径做最小表级授权：app_rw 读 integration 5 张表、pii_rw 读写 core outbox 三表 + MQ 收件箱；不放开 DMZ-only 表。
- **验证**：`pg_stat_activity` 显示 `retail_app_rw`；app_rw 查 `pii.customer_pii`/建表/查 `integration.partners` 均拒；pii_rw 查 `core.loans` 拒；冒烟全绿。
- **追问**：
  - Q：为什么不共用一个业务角色？→ 最小权限：PII 与 DMZ 必须分开；跨 schema 只给表级授权。
  - Q：运行期账号怎么保证没有 DDL？→ 迁移账号独立 + 角色实测 `CREATE TABLE` 被拒。
- **诚实边界**：生产密钥托管与轮换仍属运维；本地用 V1 开发口令。

### 案例 7｜5 类密钥弱默认值 → 启动 fail-fast

- **场景/目标**：JWT/PII/附件/MQ 密钥漏注入时，服务不能静默使用 dev 弱密钥。
- **我的边界**：配置、密钥策略、启动门禁。
- **现象/难点**：
  - 各服务 `application.yml` 和代码 `@Value` 都带 `dev-only-...` 默认值；漏注入即静默启用弱密钥。
  - `AuthController` 还自己读了一份客户密钥，和验签器可能不一致。
- **排查**：
  1. 全仓 `grep dev-only`，列出 5 类密钥的所有落点。
  2. 检查启动路径：缺 env 时是否有占位符失败；弱值是否还能启动。
  3. 检查签发/验签是否同源。
- **解决/取舍**：
  - 移除全部默认值；新增 `SecretPolicy`：缺失、短于 32 字节、非 dev profile 的 dev-only 弱值、两把密钥复用 → 启动失败。
  - `AuthController` 改用 `customerTokenVerifier` Bean，签发/验签单一来源。
  - 本地 `scripts/dev-secrets.sh` 显式激活 dev profile；生产不 source。
- **验证**：缺 env 启动 EXIT 1；弱值非 dev EXIT 1；dev 值冒烟全绿；661 测试。
- **追问**：
  - Q：密钥轮换做了吗？→ PII 有 `key_version`；JWT 自动轮换未做；托管/轮换是上线运维项。
  - Q：为什么 dev profile 能放过？→ 仅本地显式激活，生产不配置该 profile。
- **诚实边界**：没有接 Vault/KMS；不声称托管完成。

### 案例 8｜迁移与运行期解耦：独立 db-migration 作业

- **场景/目标**：多副本发布时，迁移不能绑在某个服务启动上；运行账号不能执行 DDL。
- **我的边界**：迁移作业、发布顺序、启动编排。
- **现象/难点**：
  - 只有 retail-core 开 Flyway；迁移时点与一个运行单元隐式绑定。
  - 服务滚动发布时，旧/新版本可能同时在线，迁移顺序不可控。
- **排查**：
  1. 检查各服务 `flyway.enabled` 与迁移账号。
  2. 在空库上验证迁移是否可从零执行。
  3. 用 app_rw 直连验证 `CREATE TABLE` 被拒，确认运行账号不能迁移。
- **解决/取舍**：
  - 新增独立 `db-migration` 模块：Flyway 作业，迁移账号执行、无端口、非长驻。
  - 所有服务（含 retail-core）`flyway.enabled=false`；启动脚本先跑迁移，失败 fail-closed。
  - 发布顺序固定为“先迁移、再滚动发布”；多副本迁移必须 expand/contract。
- **验证**：空库从零迁移 22 条 / 62 个关系对象；默认库 no-op；不可达库 EXIT 1、缺口令 EXIT 2；冒烟时 retail-core 日志零 Flyway。
- **追问**：
  - Q：为什么不每个服务各跑 Flyway？→ 重复执行、顺序不可控、运行账号会拿到 DDL。
  - Q：迁移失败怎么办？→ 作业非 0 退出，发布停止；服务不启动。
- **诚实边界**：生产发布流水线需要显式加“执行迁移 job”步骤，属于部署编排接入。

### 案例 9｜出站调用失控：策略档 + 熔断 + 资金不重试

- **场景/目标**：外部调用必须有统一超时、重试上限、熔断与异步补偿，且资金/写入不能被自动重试放大。
- **我的边界**：共享 outbound 机制件 + 适配器迁移。
- **现象/难点**：
  - Feign 默认 connect 10s / read 60s；9 处 JDK 客户端超时不一致；全部无熔断。
  - “统一重试”如果无差别加，会在银行代付/报送上造成重复资金动作。
  - DMS 结果通知失败没有持久化重试。
- **排查**：
  1. 审计 9 处客户端 + 3 个 Feign 门禁，按动作分类：查询/写入/资金/转发/咨询。
  2. 检查每类调用的幂等键是否稳定；随机键无法安全重试。
  3. 用故障桩验证：超时、503、4xx、连续失败。
- **解决/取舍**：
  - 7 个策略档：gate / gate-raw / query / write / advisory / financial / forward。
  - JDK `HttpClient` 封装 + 三态熔断；Feign `FeignBuilderCustomizer`；稳定幂等键。
  - **资金 / 写入 / 锁内转发代码级不重试**，不依赖配置约定。
  - DMS 失败落 `outbound_tasks`：1m/5m/30m/2h/6h → DEAD → 人工重触发。
- **验证**：银行 503 只打一次；熔断半开；真实 PG 状态机 SQL；冒烟全绿。
- **追问**：
  - Q：为什么银行代付不重试？→ 超时不代表没扣款，自动重试可能重复资金动作；用幂等键 + 查询/人工补偿。
  - Q：为什么异步任务不用 MQ？→ 这是单服务持久化重试状态机，落库更可控；MQ 只是削峰层。
- **诚实边界**：真实机构未接入，验证基于模拟器和故障桩。

### 案例 10｜MQ 明文 PII 风险：密文信封 + 默认关闭

- **场景/目标**：MQ 只做 outbox 之上的削峰层，broker 上不能出现明文个人信息。
- **我的边界**：密文信封与 MQ 适配器。
- **现象/难点**：
  - broker 落盘消息永久保留，明文 PII 不可撤回。
  - 引入 MQ 后如果取代 outbox，会丢失本地事务原子性。
  - broker 不可用时如果静默降级同步执行，会出现重复投递和不可预期时序。
- **排查**：
  1. 列出事件 payload 白名单与禁止键。
  2. 检查 MQ 生产端是否在事务提交后发送、是否只发密文。
  3. 用真实 broker 回读原始消息体，验证无明文 PII。
- **解决/取舍**：
  - AES-GCM 密文信封 + 8 键白名单；明文 PII 键默认拒绝。
  - outbox 仍是唯一真相源；MQ 只在中继之后，默认关闭。
  - 消费侧 `(envelope_id, consumer)` 幂等；同一 handler 两个入口，不写两份业务逻辑。
  - broker 不可用显式失败，不静默降级同步。
- **验证**：真实 RocketMQ 活体测试；回读 broker 原始消息体无明文 PII；重复投递幂等；关闭态冒烟 11/11。
- **追问**：
  - Q：为什么引 MQ？→ 削峰；不是一致性方案。
  - Q：为什么默认关闭？→ 零回归；开启后同一 handler 两入口。
- **诚实边界**：未建生产 MQ 集群；broker 只本地单节点验证。

### 案例 11｜JDBC → MyBatis：改造不改语义

- **场景/目标**：持久层全量换 MyBatis 注解 SQL，但 SQL 语义、仓储签名、事务边界、对外接口不变。
- **我的边界**：持久层改造。
- **现象/难点**：
  - ORM 隐式行为会改变读语义：MyBatis 一级缓存默认 SESSION，可能读到旧行。
  - NULL 映射口径不一致；唯一键冲突处理不当会让 PG 事务 aborted。
- **排查**：
  1. 逐条对照原 JDBC SQL 与 MyBatis 注解 SQL。
  2. 用真实 PG 验证 NULL、唯一键、乐观锁、自增回填。
  3. 跑全量单测/冒烟/E2E 对比行为。
- **解决/取舍**：
  - Mapper 注解 SQL，无 XML / 无 JPA；`RowValues` 统一 NULL 口径（`getLong`→0、`getString`→null）。
  - `local-cache-scope: STATEMENT`，对齐原“每次读都落库”的语义。
  - 唯一键幂等统一 `ON CONFLICT`；`@Options(keyColumn=...)` 回填自增主键。
  - `@MapperScan` 显式列单一包，不做全包扫描。
- **验证**：661 测试 0 失败；真实 PG 三处 `ON CONFLICT` 实测；冒烟/E2E 零回归；迁移字节未动。
- **追问**：
  - Q：为什么不用 JPA？→ 金融 SQL 需要可控的锁/索引/冲突语义，ORM 隐式行为不可接受。
  - Q：怎么保证没改语义？→ 逐条 SQL 对照 + 真实 PG + 全量回归；改造前后接口/事务边界不变。
- **诚实边界**：是持久层重构，不改业务规则。

### 案例 12｜所有权解除：两态分离与外部回执权威

- **场景/目标**：解除文件“出具”不等于车辆登记“完成”；只有外部登记回执能推进终态。
- **我的边界**：title-release 领域与状态机。
- **现象/难点**：
  - 业务上容易把“文件已发”当成“解押完成”，造成物权风险。
  - 合作方自证、我方代录都可能被误当成外部回执。
- **排查**：
  1. 画解除八步状态图，区分 `DOCUMENTS_ISSUED` 与 `REGISTRATION_CONFIRMED`。
  2. 检查证据链：文件、交付、外部申请、回执、权威性判定。
  3. 构造负例：合作方自证、代录、回执缺失。
- **解决/取舍**：
  - 8 态状态机；终态不可逆；状态变更只走聚合方法。
  - 外部回执是唯一权威；`PARTNER_SELF_REPORT` 拒绝；`MANUAL_RECORDED` 只能作为中间态。
  - 证据链八条闭合条件全部满足才可进第 7 步。
  - 附件本地存储：SHA-256、预签名、路径穿越防护、受控下载。
- **验证**：状态机单测、E2E S12、X-10 负例、回执幂等；文件/登记两态分离。
- **追问**：
  - Q：回执没到怎么办？→ `MANUAL_RECORDED` 中间态，继续等外部回执；不能提前闭环。
  - Q：为什么不用合作方自证？→ 自证不具备登记机关权威性，不能作为解除完成证据。
- **诚实边界**：未接真实登记机关；按协议与模拟器验证。

### 案例 13｜状态机：领域是唯一事实源，引擎只是执行器

- **场景/目标**：引入状态机引擎，但不让引擎成为第二份状态图。
- **我的边界**：状态机底座与接线。
- **现象/难点**：
  - 引擎配置容易和领域枚举各写一份，时间一长就漂移。
  - 领域层不能引 Spring，否则无法纯 JUnit 测试。
- **排查**：
  1. 对照领域 `graph()` 与引擎配置的边集。
  2. 找“领域没有变更入口、引擎却登记了”的边。
  3. 检查 domain 是否 import Spring。
- **解决/取舍**：
  - 领域枚举 `graph()` 是唯一事实源；引擎边由它生成。

  - 引擎只做执行器，不落库；领域方法仍是合法性最终裁决。
  - domain 零 Spring，纯 JUnit 可跑；接线只放服务内 `*.application.statemachine`。
- **验证**：状态机单测、无效迁移拒绝、装配 fail-fast、domain 零 Spring 扫描。
- **追问**：
  - Q：为什么用引擎？→ 统一编排/守卫/动作；但事实源仍是领域。
  - Q：引擎能改状态吗？→ 不能绕过领域方法；状态权威在数据库 + 领域规则。

| 启动报 `ConflictingBeanDefinitionException` | 对比 jar 内类路径与包声明，发现 VSCode JDT 按目录输出、Maven 按声明包输出 | 修正包声明；全仓扫描包/路径一致性 | 工具链差异导致的同名 Bean |
| Gateway 启动 `NoSuchMethodError: HttpHeaders.headerSet()` | `mvn dependency:tree` 看到 Spring Framework 6.1.6 与 Gateway 4.1.6 不匹配 | 显式前置 Spring Framework BOM 到 6.1.15 | 依赖收敛与 BOM 顺序 |
| CI 不触发 / 构建失败 | 看 workflow 触发分支是 `main`，仓库是 `master`；构建依赖独立 contracts 仓 | 改触发分支 + 增加 build job + 克隆/安装 contracts | CI 死链与依赖仓 |

## 6. 高频追问 Q&A（按主题）

### 6.1 一致性与幂等

**Q：为什么不用分布式事务/Seata？**
A：账务核心不拆，入金核销+余额+债权终态在同一本地事务；跨服务事后同步用 outbox + 幂等，不引入全局锁和回滚日志。每一环可验证、可重放。

**Q：Outbox 和 MQ 是什么关系？**
A：outbox 是唯一真相源，跟业务表同事务；MQ 只是 outbox 之后的削峰缓冲，默认关闭，不参与事务、不取代 outbox。

**Q：at-least-once 怎么保证业务不重复？**
A：消费幂等三层：`(event_id, consumer)` 认领、业务唯一键、状态机/唯一索引兜底；不追求 exactly-once。

**Q：多实例消费怎么防重复？**
A：`event_consumptions` 原子认领 `PENDING/FAILED → PROCESSING` + 5 分钟租约；状态写只允许认领者；游标 `GREATEST` 只前进；未抢到本轮跳过。

**Q：锁和唯一索引谁保证正确性？**
A：唯一索引/乐观锁是正确性来源；分布式锁只收敛并发窗口。锁不可用 fail-closed 拒写，不降级放行。

### 6.2 数据库与持久层

**Q：为什么核心账务不拆库/不拆服务？**
A：余额、核销流水、债权终态必须同生共死；拆开就要分布式事务或补偿，资损风险大于收益。先用 schema 隔离，按写入集冲突/流量触发器再演进。

**Q：为什么捕获唯一键异常再重读不行？**
A：PostgreSQL 事务内唯一键错误会把事务置为 aborted，后续 SQL 全部失败；必须用 `ON CONFLICT` 原子语义。

**Q：为什么 MyBatis 不用 JPA？**
A：金融 SQL 需要显式控制锁、索引、冲突、NULL 口径；JPA 隐式行为不可接受。MyBatis 注解 SQL + `RowValues` 让语义可见可测。

**Q：一级缓存怎么处理？**
A：降到 `STATEMENT` 级，对齐原 JdbcTemplate“每次读都落库”的语义，避免同一事务读到旧行。

**Q：余额对拍为什么不容差？**
A：容差会让系统性偏差长期潜伏；精确相等让偏差当天暴露、当天可查。

### 6.3 安全与合规

**Q：员工和客户 token 怎么隔离？**
A：两套密钥、两套 issuer/audience、验签层强制 `subjectType`；员工 token 过客户验签/反之都 401；审计 actor 取验签身份。

**Q：PII 加密后怎么检索？**
A：AES-256-GCM 随机 IV 存密文；需要精确检索的字段另存 HMAC-SHA256 指纹列，不存明文、不用确定性加密。

**Q：PII 会进日志/事件吗？**
A：事件 payload 白名单默认拒绝 PII 键；日志脱敏；MQ 只允许密文信封；审计只记字段名/用途，不记明文值。

**Q：运行期账号怎么保证不是超管？**
A：数据源按角色配置 + 启动门禁拒绝 postgres/未知角色/弱口令；Flyway 独立迁移账号；`pg_stat_activity` 和权限拒绝实测。

**Q：密钥轮换做了吗？**
A：PII 有 `key_version`，支持旧版本重加密的演进方向；JWT 自动轮换未实现；托管与轮换是上线运维项，不冒充已完成。

### 6.4 外部集成与故障

**Q：银行代付为什么不自动重试？**
A：超时不代表没扣款；自动重试可能重复资金动作。用稳定幂等键 + 查询/人工补偿；只有查询类可重试。

**Q：熔断半开怎么做的？**
A：连续失败达阈值打开；打开期直接拒绝；到期半开只放一个探针；成功闭合/失败重开；按 channel 隔离。

**Q：外部机构没接进来，怎么证明功能对？**
A：防腐层 + 双模适配器 + 零依赖模拟器；按协议做双向闭环和负例；真实接入只换 URL。不声称已真实联调。

**Q：Redis 挂了限流怎么办？**
A：生产 fail-closed 503；本地 dev 显式 fail-open；Sentinel 高可用 + 故障转移；ERROR 标记告警（10s 节流）。

**Q：MQ broker 挂了怎么办？**
A：显式失败，不静默降级同步；outbox 仍在本地事务里，恢复后重投；MQ 不是真相源。

### 6.5 发布与运维

**Q：多副本怎么发布迁移？**
A：独立 `db-migration` 作业先执行；服务全部 `flyway.enabled=false`；迁移失败停止发布；多副本迁移用 expand/contract。

**Q：为什么迁移账号和运行账号分开？**
A：运行账号不应有 DDL；迁移账号只在迁移期使用；G-DB-3。运行账号 `CREATE TABLE` 被拒实测。

**Q：CI 跑什么？**
A：文档一致性 + 术语幂等 + 全量构建 + 661 单测；构建前克隆并安装 contracts 共享 jar。

### 6.6 个人贡献与真实性

**Q：这个项目全是你做的吗？**
A：不是。团队交付，我负责 [主责包]；其他模块/前端/真实联调是同事或下一阶段。我只写我负责的部分。

**Q：系统上线了吗？有生产数据吗？**
A：没有。完成全链路仿真、模拟器、真实浏览器验收；未接生产流量和真实客户。外部机构联调与合规验收是下一阶段。

**Q：你最大的贡献是什么？**
A：把“资金正确性/跨服务一致性”从口号变成可验证机制：三层幂等、outbox 多实例、唯一索引回调、fail-closed 门禁、迁移解耦；并用单测/冒烟/真实 PG/broker 验证。

**Q：如果重做，你会改什么？**
A：更早把可观测性和告警纳入设计；更早做多实例/故障注入；把外部协议和模拟器作为一等交付物；减少“先写实现再补门禁”的返工。

## 7. 排查方法论（通用，面试官很吃这一套）

### 7.1 先分类，不要一上来改代码

| 类型 | 典型现象 | 首选证据 |
|---|---|---|
| **语义错误** | 结果不符合业务规则 | 领域状态图、SQL 结果、事件 payload |
| **并发竞态** | 偶发重复/覆盖/丢失 | 并发复现、唯一索引、事务隔离、锁等待 |
| **环境差异** | 本机好、WSL/CI 挂 | 行尾、JDK、时区、端口、依赖树 |
| **依赖故障** | 超时/500/连接拒绝 | 异常链、连接池、Redis/broker/DB 状态 |

### 7.2 五步法

1. **定义可证伪的现象**：不是“好像有问题”，而是“同一合同并发 5 次出现 2 条代付”。
2. **最小复现**：单测/真实 PG/真实 broker/真实浏览器；能隔离就隔离。
3. **收集证据**：日志、异常链、SQL、`pg_stat_activity`、`flyway_schema_history`、`EXPLAIN`、broker 回读、`dependency:tree`、`git ls-files --eol`。
4. **验证假设**：一次只改一个变量；先证伪，再修复。
5. **固化回归**：补单测/冒烟/门禁；把教训写进文档，避免同类问题复发。

### 7.3 高频证据清单

- 并发/唯一键：真实 PG 并发、`ON CONFLICT`、事务 aborted 现象；
- 多实例：两个进程/两个 consumer、租约过期、游标回退；
- 外部依赖：停 Redis/broker、故障桩、异常链；
- 环境：`bash -n` 不够，要看 `git ls-files --eol`；
- 依赖：`mvn dependency:tree`、BOM 顺序；
- 迁移：空库从零、默认库 no-op、`flyway_schema_history`、app 角色 DDL 拒绝。

## 9. 使用红线

1. **只写真实做过的包**；本文是菜单，不是让你全选。
2. **数字只用仓库可验证的**：18 模块、12 长驻单元 + 迁移作业、V1–V22、62 个关系对象、661 单测；不写线上指标。
3. **系统未上线**：明确说“全链路仿真 + 模拟器 + 浏览器验收”，不冒充生产经验。
4. **外部机构未真实接入**：说协议/模拟器/防腐层，不说已联调。
5. **法律与合规效力**：只讲系统机制与留痕，不下法务结论。
6. **团队成果**：明确边界；不是自己写的代码，不认领。
7. **每个主责包至少准备一个“踩坑/排查”故事**；没有失败故事的“负责”，面试官会认为是“参与”。
8. 面试前把本文 §4 的 3 个案例按“现象→排查→解决→验证”口述一遍，控制在 3–5 分钟。
