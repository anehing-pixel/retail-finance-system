## 1. 项目名称与一句话定位

**项目名称**：日本 C 端个品分期消费金融核心系统（新车零售金融 · 信贷全生命周期）

**一句话定位**：面向消费者的个人分期信贷核心系统，覆盖**进件 → 征信 → 授信 → 合同 → 放款 → 账务 → 贷后 → 所有权解除**全链路，
按持牌消费金融合规口径设计（同意门禁 / 放款三重门禁 / 支付能力预估额 / 征信报送与对账闭环）。

**业务形态**：消费者在销售店购买新车并提交分期申请 → 个人征信查询与收入证明审核 → 签订合同 →
信贩向销售店代付车款 → 交车并登记**所有权保留** → 消费者按月还款 → 结清或提前结清 → 出具**所有权解除文件**并办理**名义变更**。

**交易形态口径（防误解，面试必背）**：主形态是**个品分期（个别信用购买斡旋，属《分期付款销售法》体系）**——
钱不直接给消费者，而是信贩**向销售店代付车款**、消费者**向信贩分期支付**；担保是**所有权保留**
（车辆检验合格证「所有者」栏登记为信贩），**既不是抵押，也不是无担保信用贷**；额度基准是
**个别支付能力预估额**，而不是贷金业法的总量规制。系统按**双形态并行**建模（个品分期 + 汽车贷款，
形态差异收敛在 4 个策略点：法定书面文件 / 支付能力预估额 / 征信报送 / 结清计算），每笔申请必填形态字段。

## 4. 简历条目（主推版 · 6 条 · 按服务展开）

> **负责 C 端个品分期消费金融核心系统 4 个微服务的端到端交付**（Spring Cloud 微服务，12 个部署单元），
> 覆盖进件→征信→授信→合同→放款→账务→贷后→所有权解除全信贷生命周期。

1. **架构与领域建模（团队主导）**：完成 12 个限界上下文的领域发现与上下文映射，按"担保物形态不同必拆、通道能力相似必合"的原则划定服务边界，落地 10 业务服务 + 网关 + DMZ 共 12 个部署单元；沉淀 62 张表 / 4 schema 的数据架构与 14 份架构决策记录（ADR），并以"契约冻结 + 号段登记 + 并行写入集互斥"的工程纪律支撑多工作包并行开发无冲突合入。

2. **retail-core —— 核心账务（刻意不拆，保证强一致）**：负责债权、还款计划、代付、入金核销与结清，**刻意不拆成独立服务**——入金核销、余额与债权终态必须落在同一笔本地事务，拆开必然引入分布式事务或补偿。落地放款前**"合同 / 同意 / 审查"三重 fail-closed 门禁**（任一超时、拒绝或状态未知即拒付并整体回滚），叠加**"请求指纹 + 数据库唯一索引 + 业务唯一键"三层幂等**，从机制上保证一份合同的代付只发生一次；入金核销严格按"费用 → 利息 → 本金"顺序拆分、期次内先息后本，超额入金转人工工单而不自动分摊；**余额对拍要求精确相等、不容差**（余额 ≡ 代付本金 + 手续费 + 利息 − 已核销本金），并落地提前结清金额公式与减免额上限守卫；到期批量用**单条 SQL 抢占锁**（唯一约束 + 冲突更新 + 条件更新）保证不重复执行、失败可重试、僵尸 RUNNING 可接管；核心链路状态迁移接入**状态机引擎底座**（领域状态图仍是唯一事实源，引擎不侵入领域层，`domain` 继续零 Spring 依赖、纯 JUnit 可跑）；
另把「36 期 0 息」这类产品档位做成**版本化配置表**（V18 新增产品目录，同码多版本 + 生效区间），生成计划时按「授信覆盖 > 档位默认」合成参数并落**快照**（档位码 / 版本 / 利率基点），**改配置不回改历史计划**。

3. **underwriting-service —— 个人审查与授信决策**：以聚合根 + 状态机实现审查案件流转（状态变更只能走聚合方法、终态不可再迁移），落地三条硬不变式：**职责分离**（复核人与决定人不可为同一人，违反直接拒绝）、**征信查询未完成不得决定**、**决定必须锚定有效同意**（同意门禁 fail-closed，取不到证据一律拒绝而非放行）；支付能力预估额抽象为可替换策略端口，按 PASS / FAIL / REFER 三态出具结论并落策略版本号（口径变更走配置不改代码），同时对外提供放款前审查门禁实现。

4. **bureau-service —— 个人征信查询 / 报送 / 异议全链路**：设计防腐层隔离征信机构差异（外部报文经适配器转内部命令，机构未接入时以挡板实现承接，业务代码零改动）；实现查询与报送双通道、报送执行闭环（逾期变化、结清两类事件驱动触发）、失败人工补发通道与报送日批（抢占锁防重复执行）、报文与查询留痕、异议申诉时限管理；所有报送口径（机构组合、报送周期、异议时限、策略开关）配置化，落实"口径变更走配置不改代码"。

5. **title-release-service —— 所有权保留与解除闭环**：建模 8 态解除订单状态机（文件准备 → 文件出具 → 外部提交 → 回执确认 → 办结），用状态机强制三条业务红线：**"解除文件已出具"与"登记已完成"两态分离**、我方见证代录不得跳过外部回执、终态不可再迁移；配套证据链策略与本地附件存储（SHA-256 校验、预签名上传下载、路径穿越防护、受控下载），并把唯一键冲突从"抛 500"改为"幂等返回既有记录"；外部登记回执的**回调幂等**由**表达式唯一索引**兜底——外部方换一个 nonce 重推同一业务回执，也不产生第二条回执、不重复推进解押状态、不重复发闭环事件。

6. **跨服务契约底座 + 外部对接与质量工程**：跨服务**同步**只保留**代付前 fail-closed 同步门禁**（合同 / 同意 / 审查）的 Feign 契约——任一超时、拒绝或状态未知一律拒付并整体回滚，事后同步一律走 Outbox 事务性发件箱 + 轮询投递（at-least-once + 消费幂等 + 失败进 DEAD 不阻塞链路）；配套 17 类领域事件常量与**事件载荷白名单守卫（默认拒绝）**，从发布端杜绝个人信息进入事件载荷；主笔外部机构字段级对接协议（征信查询与报送、银行代付、身份核验、销售店系统结果、所有权保留登记回执、书面送达）共 14 条通道规格与通用报文信封规范，自研零依赖 Node 外部机构模拟器作为六向对端，配合"配置切换挡板 / 真实 HTTP"双模适配器完成双向闭环联调，联调期暴露并修复并发幂等竞态、调度线程缺失认证上下文、浏览器请求规范等 4 个真实缺陷；建立分层断言体系（走网关冒烟 33 + API 全链路 104 + 模拟对接 34 + 前端页面 46 + 浏览器点击级 30 + MQ 通道 11 + 锁专项冒烟 20 + 限流专项 62，共 340 条）与 12 进程一条命令编排，MQ 削峰轮另修复 3 个真实缺陷（包声明与目录不一致致同名 Bean 冲突、跨零点日期钉死用例、CRLF 脚本致 WSL 解析失败），锁轮另修复 1 个真实缺陷（Redis 宕机时 Redisson 抛包装异常导致 500，应为 503 fail-closed），配套 15 项文档一致性机器校验并接入 CI，构建 656 单测 0 失败；

## 7. 面试讲述主线（3 分钟讲完）

1. **服务拆分是领域建模的结果，不是起点**：先做 12 个限界上下文的领域发现与上下文映射，再定服务边界。
   拆分判据只有两条——担保物形态不同必拆、通道能力相似必合；不讲"生命周期长短"这类模糊标准。
   我负责的 retail-core / underwriting / bureau / title-release 四个服务，正好对应"核心账务""个人审查""外部征信通道""所有权担保物"四类不同上下文——授信决策、征信、账务、物权解除连成一条闭环。
2. **中台复用要画界**：复用"能力"（契约 jar、错误码、事件常量），不复用"数据和状态"，否则中台退化为分布式单体。
   落法是契约冻结——我冻结 Feign 门禁契约与 17 类事件常量表之后，各工作包并行开发不得新增未登记契约。
3. **金融系统的默认姿势是 fail-closed**：拿不到同意证据、门禁超时、状态未知，一律拒绝而不是放行。
   真实教训：事件驱动的征信报送在调度线程执行、没有请求上下文，认证直接 401，报文永远发不出去——
   修复方式是给机器场景签发服务身份 token，而用户场景仍坚持零信任透传。**这个缺陷单测 mock 掉了、
   API 级 E2E 也没覆盖，是接了真实对端之后才暴露的。**
4. **合规门禁之外还有一致性**：Outbox 保证"状态变更"与"事件产生"同事务；投递失败进 DEAD 并保留人工补发，
   一条坏事件不阻塞整条链路。
5. **外部机构是长周期日历依赖，不能阻塞开发**：自建模拟器把"等外部"变成"对模拟器验收"，
   机构真正接入时只换 URL，报文差异由双模适配器消化。

## 8. 高频追问与应答骨架

**Q：Outbox 为什么不直接发消息？**
本地事务写业务表与写 outbox 表在同一事务内，保证状态变更与事件产生原子；投递由后台轮询完成，失败落人工补发表。
直接发消息无法保证两者原子性——这才是选型的根本原因。

**Q：nonce 防重放怎么保证原子性？**
以数据库唯一约束原子写入，重放写不进去即 409；不做"先查后插"（有竞态窗口）。

**Q：审查服务的职责分离是怎么实现的？**
聚合根层面硬阻断：复核人与决定人不可为同一人，违反直接抛权限错误码；状态迁移只能走聚合方法，
不提供任何"直接改状态"的入口，仓储层只允许按状态机允许集迁移。

**Q：征信机构还没接进来，你这个报送功能怎么算完成？**
业务侧口径（机构组合、周期、异议时限、开关）已全部配置化并落库留痕，机构通道走防腐层，
当前用挡板实现承接——外部机构签约是日历依赖，系统侧已就绪；对外协议 v1 已定稿可直接用于联调。

**Q：为什么本地要自研模拟器？**
外部机构调研与签约是长周期日历依赖。零依赖 Node 模拟器实现六向对端（征信 / 银行代付 / 身份核验 / 销售店 / 送达 / 入金文件），
把"等外部"变成"对模拟器验收"。回报是抓出 4 个真实缺陷：保留登记并发竞态、调度线程缺认证上下文、
构造器歧义导致启动失败、GET 请求携带空 body 违反浏览器规范（只有真实浏览器触发）。

**Q：为什么核心账务不拆成独立服务？**
拆开就必须引入分布式事务或补偿，而"入金核销 + 余额 + 债权终态"必须同生共死——余额与终态不一致会直接变成资损。
所以账务保持单服务单事务，靠模块边界而不是服务边界做拆分。

**Q：三层幂等为什么每一层都要？**
请求指纹防"同键不同内容"的误重放；数据库唯一索引兜底并发插入；业务唯一键兜底"换了幂等键也挡不住重复代付"——
三层各堵一个不同的漏洞，缺一层就会出现一类漏网的重复扣款。

**Q：余额对拍为什么不允许容差？**
容差会让系统性偏差长期潜伏（每天差 1 日元，几年就是资损）；精确相等让任何偏差当天暴露、当天可查。

**Q：数据库为什么不一步到位拆库？**
共库不同 schema 起步：事务边界简单、跨域查询明确、迁移成本低；同时预登记演进触发器（写入集冲突 / 流量阈值）。
隔离性先用独立实例 + 独立迁移号段 + 独立密钥保障。

**Q：你们这套东西上线了吗？**
**没有**。系统已完成全链路对模拟器的验证与真实浏览器点击级验收，但未接入生产流量、未承接真实客户。
外部机构接入与合规验收是下一阶段，且已定稿字段级协议作为谈判基线。（**如实说，不要吹线上经验。**）
