> **用法**：本文件是**菜单**——每个微服务都写清"它到底做了什么、含金量在哪、可直接写进简历的句子、被追问时怎么答"。

**项目背景（放在所有条目之前）**：日本 C 端个品分期消费金融核心系统，Spring Cloud 微服务，
12 个部署单元（10 业务服务 + 网关 + DMZ），覆盖进件→征信→授信→合同→放款→账务→贷后→所有权解除全信贷生命周期。

## 1. gateway（18081）· 统一入口与路由治理

**关键实现**
- 精确路由在前、兜底路由在后；每个服务的**路由段预分配**（并行开发时各改各的段，不互相覆盖）。
- URI **双模**：默认 `lb://服务名`（注册中心），可用 `ROUTE_*` 环境变量覆盖为直连——本地无 Nacos 也能起整栈。
- **不启用** discovery locator（不自动把服务名暴露成路由），所有路由显式声明，避免"服务起来了但路由是自动生成的"这种隐性接错。
- `X-Request-Id` 请求 ID 贯穿全链路（各服务日志与审计用同一 traceId 串联）。

**简历条目候选**
> 负责 API 网关的路由治理：设计"精确规则在前、兜底在后"的切流顺序与路由段预分配机制，支持
> `lb://` 与直连双模 URI（无注册中心环境可整栈启动），并统一 `X-Request-Id` 贯穿全链路，
> 使 12 个服务的请求可按同一 traceId 串联排查。

**深挖备料**：为什么不用自动路由发现（可控性 vs 便利性）；双模 URI 的本地/生产差异；
路由段预分配如何避免并行开发互相覆盖（呼应"写入集互斥"纪律）。

## 2. external-api / DMZ（18091）· 外部机构入站安全闸 ★高含金量

**关键实现**
- 七道校验链**顺序固定不可调换**：合作方已登记 → 时间戳新鲜度（±300s）→ nonce 防重放 →
  签名常量时间比较 → 合作方状态 → scope 授权范围 → IP 白名单。
- **nonce 用数据库唯一约束原子写入**（重放写不进去即 409），不做"先查后插"（有竞态窗口）。
- 签名比较用**常量时间**比较，防时序侧信道；签名校验**先于** scope/IP，避免对伪造请求做无谓的后续校验。
- 成败**都**落 `integration.call_logs`（append-only，只追加不修改）；失败按语义区分 401 / 403 / 409。
- 外部回调（如登记机关回执）过闸后由**系统服务身份 token 转发**给内部服务——外部方永远拿不到内部凭据。

**简历条目候选**
> 独立设计并实现 DMZ 外部接入安全区：按"登记校验 → 时间戳新鲜度 → nonce 原子防重放 → HMAC 签名常量时间比较
> → scope 授权 → IP 白名单"固定顺序执行七道关卡，失败按 401/403/409 区分语义，成败统一落 append-only 调用日志；
> 外部回调经系统服务身份转发入内部，外部方不持有任何内部凭据。

**深挖备料**：为什么 nonce 要用唯一约束而不是查后插；为什么签名要在 scope/IP 之前；
外部方拿到的只是回执投递入口，内部调用仍走零信任；呼应"个人信息不入日志"红线。

## 3. auth-service（8091）· 双主体认证 ★高含金量

**关键实现**
- **员工 / 客户两套密钥**（`RETAIL_JWT_SECRET` / `RETAIL_CUSTOMER_JWT_SECRET`），两套 issuer + audience。
- **主体类型在验签层强制**：员工密钥签的客户 token、客户密钥签的员工 token、主体类型声明不符，一律 401。
  不存在"先过认证、后面再用注解挡主体"的窗口。
- **401（认证失败）与 403（授权失败）严格区分**。
- 角色 → 权限点链路打通（角色进 token、权限点进 perms）；除管理员外不预置权限（最小授权原则：宁可后配，不可先滥）。
- 客户侧无 RBAC——客户 token 不带角色，避免"把客户当员工"的越权路径。

**简历条目候选**
> 设计员工 / 客户双主体认证体系：两套独立密钥与 issuer/audience，主体类型在验签层强制校验，
> 杜绝"客户令牌当员工令牌使用"的越权路径；严格区分 401 与 403，并在令牌中内嵌角色与权限点，
> 权限采用最小授权原则（默认不预置、后台按需授予）。

**深挖备料**：为什么必须两把密钥（同一密钥签发的两类令牌无法在验签层区分主体）；
双主体与跨项目中台的关系（机制共享、语义隔离）。

## 4. customer-service（8092）· 个人信息金库与同意管理 ★高含金量

**关键实现**
- **字段级 AES-256-GCM 加密**（密钥与 JWT 密钥、账号加密密钥分离）+ **HMAC-SHA256 检索列**（精确匹配用指纹，
  不解密全表扫）+ `key_version` 落库支持密钥轮换。
- **默认脱敏出口**：姓名只显姓、电话露末 4 位、地址只到市区、收入只露末 4 位、出生日期全打码。
- 看全量需**同时满足**权限点 + 用途声明，且**每次访问都写 `audit.pii_access_logs`**（谁、何时、为哪个客户、看了哪些字段）。
- **同意聚合**：`GRANTED → WITHDRAWN / EXPIRED`，**撤回即刻生效**阻断后续查询与报送；
  撤回不删历史（append-only 同意表 + 撤回表并存）。
- 身份核验 + eKYC 出站走适配器（双模：挡板 / 真实 HTTP），出站只传脱敏号。
- 客户自助端点只返回本人脱敏视图（主体隔离）。

**简历条目候选**
> 建设个人信息金库：姓名 / 证件 / 住址 / 收入等字段采用 AES-256-GCM 字段级加密，另建 HMAC 指纹列支撑精确检索
> 而无需解密全表，密钥版本化支持轮换；对外接口默认只出脱敏视图（姓名仅显姓、地址到市区），
> 查看全量须同时具备权限点与用途声明，且每次访问留痕到审计表。

**深挖备料**：为什么用"加密列 + HMAC 检索列"而不是全库加密或哈希（可检索 + 可解密 + 可轮换）；
脱敏规则怎么定的；同意撤回的秒级生效如何影响下游报送。

## 5. application-service（8093）· 申请受理与销售店代办

**关键实现**
- **写接口幂等三层**：`Idempotency-Key` 请求指纹 + 数据库唯一索引 + 业务唯一键；
  同键同指纹重放返回首次结果，同键异指纹直接判冲突。
- **重复申请检测**：同客户 + 同一车辆 + 时间窗内已有在途申请即拒绝（窗口配置化，默认 72 小时），
  判定逻辑是**纯函数**，候选筛选交给仓储 SQL——领域层不碰数据库。
- **销售店主数据是只读投影**：上游（中台既有经销商主数据）为权威写者，本服务只收快照；
  同步失败**降级为待人工处理状态**而不是留脏数据，人工核对后重触发。
- 消费审查结果事件回写申请状态；销售店通过系统代办提交申请。

**简历条目候选**
> 实现申请受理服务：写接口采用"请求指纹 + 数据库唯一索引 + 业务唯一键"三层幂等防重放，
> 同客户同车辆在时间窗内的重复申请直接拒绝；对接销售店侧只保留经销商主数据的只读投影，
> 上游同步失败自动降级为待人工处理，避免脏投影污染下游。

**深挖备料**：幂等键的指纹怎么算（规范化后哈希）、为什么三层都要；
"只读投影 + 失败降级"如何避免跨系统数据不一致。

## 6. underwriting-service（8094）· 个人审查与授信决策 ★★最推荐

**关键实现**
- **审查案件聚合根 + 状态机**：状态变更只能走聚合方法，终态不可再迁移，仓储不允许直接改状态字段。
- 三条硬不变式：
  1. **职责分离**：复核人与决定人不可为同一人，违反直接抛权限错误码（不是靠流程约束，是代码硬阻断）；
  2. **征信查询未完成不得决定**（防止拿未完成的数据拍板）；
  3. **决定必须锚定有效同意**——同意门禁 fail-closed，查不到同意 / 已撤回 / 已过期一律拒绝。
- **支付能力预估额抽象为策略端口**（PASS / FAIL / REFER 三态），**当前实现是挡板**（策略可关闭转人工、
  收入证明缺失转人工、超过阈值判 FAIL），结论落**策略版本号**，口径变更走配置不改代码。
- 事件驱动：消费"征信查询完成"事件推进审查；对外**提供放款前审查门禁**实现。
- 领域层零 Spring 注解，可纯 JUnit 测。

**简历条目候选**
> 独立负责个人审查与授信决策服务：以聚合根 + 状态机实现审查案件流转（状态变更只能走聚合方法、
> 终态不可迁移），在代码层硬阻断三条不变式——复核人与决定人不得为同一人（职责分离）、
> 征信查询未完成不得决定、决定必须锚定有效同意（取不到证据一律拒绝而非放行）；
> 支付能力预估额抽象为可替换策略端口并落策略版本号，口径调整走配置不改代码。

**深挖备料**：为什么职责分离要做成代码硬阻断而不是流程规范；
预估额为什么先做策略点不直接写公式（法务口径未签字，形态可能反转）；
"查询未完成不得决定"如何避免数据竞态。

## 7. bureau-service（8095）· 征信查询 / 报送 / 异议 ★★最推荐

**关键实现**
- **防腐层**：外部报文在 `acl` 包内转换为内部命令（外部 DTO 不落领域对象），机构未接入时用挡板实现承接，
  业务代码零改动；双模适配器支持切到真实 HTTP。
- **查询与报送双通道**：查询按机构组合（配置化，默认双机构）执行并留痕；报送按事件驱动触发
  （逾期阶段变化、债权结清两类事件 → 生成报送 → 状态置已发送 → 发布"报送已发送"事件 → 报文留痕）。
- **人工补发通道** + **报送日批**（批次抢占锁防重复执行）。
- **异议申诉**：受理 + 时限管理（配置化，默认 30 日）。
- **报送同意锚定**：报发送量锚定"存在且未撤销的同意"，避免无同意报送的合规事故。
- 所有口径（机构组合、报送周期、异议时限、策略开关）**全部配置化**。

**简历条目候选**
> 独立负责个人征信服务：设计防腐层隔离征信机构差异（外部报文转内部命令，未接入时以挡板承接），
> 实现查询与报送双通道、事件驱动的报送执行闭环、失败人工补发与报送日批、异议申诉时限管理，
> 并将报发送量锚定在"存在且未撤销的同意"上；机构组合、报送周期、异议时限等口径全部配置化，
> 业务规则调整不改代码。

**深挖备料**：防腐层为什么必须存在（外部报文直落领域对象 = 机构改一次改一片）；
报送为什么用事件驱动而不是同步调用（同步链路一旦超时就会拖垮核心交易）；
同意锚定如何防止"无同意报送"这种不可逆的合规事故。

## 8. contract-service（8096）· 合同与法定书面文件

**关键实现**
- 合同聚合根 + 7 态状态机：`DRAFT → DOCUMENTS_DELIVERED → SIGNED → COOLING_OFF / EFFECTIVE → TERMINATED`，
  冷静期内可取消；终态显式且互斥。
- **法定书面文件**：模板可配 + **交付留痕**（生成了、交付给了谁、何时、走的哪个通道）。
- **冷静期 8 日为占位参数**（配置可改），系统只记录状态与日期，**不实现法律效力判断**。
- 书面文件送达走通道适配器（双模：挡板 / 真实 HTTP），外部投递留痕。
- 对外**提供放款前合同门禁**（合同已生效且书面文件已交付才允许放款）。

**简历条目候选**
> 实现合同与法定书面文件服务：合同 7 态状态机约束签订、冷静期与生效路径（终态互斥、不可回退）；
> 法定书面文件按"模板可配 + 交付留痕"落地，系统只记录交付动作与时间、不做法律效力判断，
> 冷静期按参数配置以便法务确认后直接调整；同时对外提供放款前的合同门禁实现。

**深挖备料**：为什么把"效力判断"排除在系统之外（合规责任不可由代码承担）；
冷静期参数化的好处（法务一签字就生效）；送达通道为什么要留痕（争议时唯一证据）。

## 9. retail-core（8090）· 核心账务（不拆）★★最推荐

**关键实现**
- **核心账务不拆**：入金核销 + 余额 + 债权终态属于同一笔强一致事务，拆开必然引入分布式事务。
- **代付三重门禁（fail-closed）**：放款前依次问合同、同意、审查三方，任一超时 / 拒绝 / 状态未知 → **拒付并整体回滚**。
- **三层幂等**：请求指纹守卫 + 数据库唯一索引 + 业务唯一键（一份合同的代付只发生一次）。
- **银行代付适配器双模**（挡板 / 真实 HTTP），真实机构接入时只换配置。
- **核销顺序**严格按"费用 → 利息 → 本金"，期次顺序内先息后本；超额入金转人工工单，不自动分摊。
- **余额对拍精确相等、不容差**：余额 ≡ 代付本金 + 手续费 + 利息 − 已核销本金。
- **结清公式**：提前结清 = 剩余本金 − 减免额 + 手续费（减免额不得超过剩余本金，守卫在代码里）；
  正常结清只做状态迁移（末回核销完成后余额已精确为 0）。
- 到期批量用**单条 SQL 抢占锁**（唯一约束 + 冲突更新 + 条件更新）保证不重复执行，失败可重试、僵尸 RUNNING 可接管。
- **全系统唯一跑 Flyway 迁移的服务**。

**简历条目候选**
> 负责核心账务服务（刻意不拆，保证强一致）：实现放款前"合同 / 同意 / 审查"三重 fail-closed 门禁，
> 任一环节超时或状态未知即拒付并整体回滚，叠加"请求指纹 + 唯一索引 + 业务唯一键"三层幂等，
> 从机制上保证一份合同的代付只发生一次；入金核销严格按"费用 → 利息 → 本金"顺序拆分，
> 余额对拍要求精确相等不容差，并落地提前结清金额公式与到期批量的抢占锁防重复执行。

**深挖备料**：为什么核心账务不能拆（拆了就得引入分布式事务）；
fail-closed 的代价（可用性换合规）；为什么余额对拍不容差（容差会掩盖系统性偏差）；
抢占锁为什么用一条 SQL 而不是"先查后插"。

## 10. title-release-service（8097）· 所有权保留与解除 ★★最推荐

**关键实现**
- **8 态解除订单状态机**：`CREATED → DOCUMENTS_PREPARED → DOCUMENTS_ISSUED → EXTERNAL_SUBMITTED /
  MANUAL_RECORDED → REGISTRATION_CONFIRMED → CLOSED`（另有拒绝 / 过期两个终态）。
- **两态分离**：`DOCUMENTS_ISSUED` 只是"文件出具"，**不得**改写所有权保留状态——
  "文件已出"和"登记已完成"是两个不同的业务事实，混为一谈就是合规事故。
- **外部回执唯一权威**：我方见证代录（`MANUAL_RECORDED`）**不得直达**登记确认，推进必须经外部回执。
- 创建解除订单的前置条件是**债权已进入终态**（结清 / 提前结清），时序不可颠倒。
- **附件本地存储**：SHA-256 内容校验、预签名上传与下载（带有效期）、**路径穿越防护**、受控下载；
  不引入对象存储（按公司既定口径）。
- **幂等修复**：保留登记由"先查后插"改为 `INSERT ... ON CONFLICT DO NOTHING`，
  冲突时幂等返回既有记录、**不重复发事件**——这是联调中真实撞出来的 500 错误。

**简历条目候选**
> 独立负责所有权保留与解除服务：建模 8 态解除订单状态机，在代码层强制"解除文件已出具"与"登记已完成"
> **两态分离**，我方见证代录不得跳过外部登记回执（外部回执为唯一权威），且建单前置条件是债权已进入终态；
> 配套附件本地存储（SHA-256 校验、预签名上传下载、路径穿越防护）；联调中把保留登记的唯一键冲突
> 从"先查后插抛 500"改为冲突幂等返回既有记录并抑制重复事件。

**深挖备料**：为什么"出具文件"不能当"解除完成"（出文件 ≠ 登记机关办结）；
为什么附件自己存不用对象存储（公司既定口径 + 无新中间件）；
幂等修复为什么用 ON CONFLICT 而不是捕获唯一键异常（PG 事务会进入 aborted 状态）。

## 11. servicing-service（8098）· 贷后逾期与催收

**关键实现**
- **逾期天数（DPD）计算器**：自然日连续计数（跨周末节假日不间断）、宽限期配置生效但快照仍记自然日、
  取所有未结逾期期次的最大值并定位**主导逾期期次**、已结（已核销 / 减免）不计逾期。
- **阶段分层**：按逾期天数分档驱动催收策略。
- **日批调度 + 批次抢占锁**（与核心账务同构：唯一约束 + 冲突更新 + 条件更新），防重复执行、失败可重试、僵尸任务可接管。
- **催收案件状态机 + 催收动作留痕**（每次动作记录操作人、时间与依据）。
- **征信报送触发**与**同意有效性门禁**（报送前再次确认同意有效）。

**简历条目候选**
> 实现贷后服务：逾期天数按自然日连续计算并定位主导逾期期次，宽限期分配置生效、快照仍保留自然日值；
> 逾期快照与报送日批采用数据库抢占锁保证不重复执行、失败可重试；催收案件按状态机流转并逐次留痕，
> 报送触发前再次校验同意有效性。

**深挖备料**：自然日 vs 营业日的取舍（客户体感与账务一致性的取舍）；
为什么日批一定要有抢占锁（多实例 / 重试都会重复跑）；
报送前为什么还要再查一次同意（同意可秒级撤回，缓存会出事）。

## 12. recon-service（8099）· 五视点对账 ★性价比高

**关键实现**
- **INV-1~5 五条对账视点**（写进代码枚举，不是文档里的口号）：
  1. 一份合同的代付只发生一次，金额 = 债权本金约定；
  2. 余额 ≡ 代付本金 + 手续费 + 利息 − 已核销本金（**精确相等，不容差**）；
  3. 解押必须在债权终态之后，登记完成必须有外部权威回执；
  4. 任何事件载荷不含白名单外键；
  5. 查询 / 报送留痕必须锚定存在且未撤销的同意。
- **差异清单幂等重跑**：同（视点 + 实体 + 实体号）只留一行，重跑时已修复 → 标记已解决、新问题 → 新开，历史不删除。
- **批次留痕可重跑**：同（作业名 + 业务日）复用同一行，不产生第二份记录。
- 对拍走**只读视图**，其中同意锚定视图以视图属主校验底层表权限，业务角色无需直连 PII 敏感表。

**简历条目候选**
> 实现对账服务：把五条账务一致性不变量（代付唯一性、余额精确相等、解押时序、事件载荷无个人信息、
> 报送同意锚定）落成可执行的对账视点并批量跑批；差异清单以部分唯一索引保证同问题只留一行，
> 重跑幂等（已修复自动置已解决、新差异新开、历史不删），批次记录同样可重跑不重复。

**深挖备料**：为什么用"精确相等"而不是容差（容差会让系统性偏差长期潜伏）；
差异清单为什么要幂等（对账每天跑，不幂等会产生噪音淹没真问题）；
只读视图 + 属主校验的权限模型。

## 13. 怎么挑：按目标岗位组合

| 目标岗位 | 建议组合 | 理由 |
|---|---|---|
| **后端 / 资深后端** | retail-core + title-release + bureau | 账务、状态机、外部对接，最能证明"复杂业务正确性"能力 |
| **架构师** | 架构与领域建模 + 契约底座（门禁契约 + 事件白名单 + Outbox）+ DMZ + recon | 体现拆分判据、契约冻结、一致性与不变量治理 |
| **金融 / 风控合规** | underwriting + customer + bureau | 职责分离、同意门禁、征信报送与异议闭环 |
| **平台 / 中台** | DMZ + 契约底座 + gateway + recon | 安全接入、契约治理、可观测与一致性 |
| **全栈 / 前端转后端** | title-release + customer + gateway | 状态机 + 数据安全 + 端到端链路认知 |

**挑选原则**
1. **一条里只放一个服务的核心机制**，别把三个服务塞进一句话——面试官会挑最弱的那条追问。
2. 优先挑**有业务约束、可讲清"为什么"**的条目（状态机、门禁、幂等、对账），而不是"接了几个接口"这种没含量的话。
3. 数字只写能兜底的：部署单元数、服务数、单测数、断言数、表数、迁移数（见 `简历-项目经历.md` §6）。
4. **团队成果不要写成个人成果**——架构与领域建模那条记得标"（团队主导）"，你个人负责哪几个服务单独列。

## 14. 全部条目共同的红线

1. 系统**未上线、无生产流量**：不得写 QPS、用户量、交易笔数、日均处理量。
2. "日本"仅指业务法规域；被问落地细节时按"设计 + 全链路仿真验证"口径讲，不声称生产运维经验。
3. 全部数字以 `PROGRESS.md`（唯一事实源）与 `interview/简历-项目经历.md` §6 速查表为准。
4. **别把它说成"信用贷"或"无担保贷款"**：主形态是个品分期（个别信用购买斡旋，《分期付款销售法》体系），
   钱是**信贩代付给销售店**、消费者向信贩分期支付，且带**所有权保留**这一担保物权；
   额度基准是**个别支付能力预估额**而非总量规制。系统是**双形态并行**（个品分期 + 汽车贷款），
   说清"我做的是双形态"比硬套一个品类名更专业。被追问时的标准答法：

   > **Q：这算信用贷吗？**
   > *"不是无担保信用贷。主形态是个品分期——信贩向销售店代付车款、消费者向信贩分期支付，
   > 适用《分期付款销售法》，额度看个别支付能力预估额；而且有担保，车辆检验合格证的所有者栏
   > 登记的是信贩（所有权保留），结清后才解除并办理名义变更。汽车贷款那条形态我们按贷金业法建模，
   > 两者差异收敛在四个策略点。"*
